# @dshwar/policy

配额判定。只回答「能不能」,429 由网关发。

> 本项目不是 DeepSeek 官方产品,与 DeepSeek 无隶属关系。

## 判定与执行分离

本包**没有任何 HTTP 概念**。`PolicyService.check(subjectId)` 返回
`allow | deny(quota_exhausted)`,由网关把 deny 翻成 429 `rate_limited` ——
判定逻辑必须能被控制平面(V0.5.0 后台)原样复用,不能长在 HTTP 层里。

## fail open —— 与硬规则 6 的 fail closed 不冲突

计量数据取不到时**放行并落审计**,而不是拒绝。两条规则方向相反,
因为保护的东西不同:

| 层             | 失败时          | 理由                                                                                      |
| -------------- | --------------- | ----------------------------------------------------------------------------------------- |
| 身份(硬规则 6) | **fail closed** | 认不出人就放行,后果是别人的数据被看到,不可逆                                              |
| 配额(本包)     | **fail open**   | 读不到账就拒绝,后果是计量组件的故障升级成全员服务中断;放行只是几轮没被限额,账目可从审计补 |

计量是账目组件,不是安全组件。把它放进关键路径的故障域,等于造一个
「记账挂了所以谁都不能用」的事故模式。**不限流的主体连 metering 都不读** ——
有测试证明 metering 全挂时它们完全不受影响。

## 超限拒绝,不静默降级

`deny` 只有 `quota_exhausted` 一种,类型层可穷举。**本包永远不会回答
「换个便宜模型继续」** —— 降级是 `@dshwar/model-router` 的显式配置。
两件事混在一起,用户就无法回答「我为什么被换了模型」。

## 余额不缓存

`tokenUsed` 每次判定从 metering 现算。缓存的余额会让「提额」变成
「提额并等缓存过期」,而运维提额之后的第一句话就是「怎么还是 429」。
有端到端测试:PATCH 提额后下一轮立即恢复。

## 周期

默认 UTC 自然月(`monthlyPeriod`)。上个周期的用量不计入本周期,
周期翻转即从零累计。要按合同周期计费,实现 `BillingPeriod` 接口注入。
