# 移动端 SDK 的生成方式 —— 手写 Node 渲染器,不引 openapi-generator

日期:2026-08-18 · 状态:已裁决(V0.8.0 Session 0)· 关联:D9

> **起手式(CLAUDE.md 设计准则)**:第一问不是「生成器跑没跑」,
> 而是**「生成器坏掉时谁会红」**。所以本文先穷举坏法,再决定用什么工具 ——
> 反过来做的话,会选出一个跑得起来但没人盯着的生成器。

---

## 一、先答「谁会红」——四种坏法,四道不同的防线

**一个生成器有四种坏法,它们在输出上长得都像「生成成功」。**

| #   | 坏法                      | 现象                                         | 谁会红                                 |
| --- | ------------------------- | -------------------------------------------- | -------------------------------------- |
| 1   | 改了契约**没重新生成**    | 产物是旧的,调用方拿到过期类型                | **同步断言**:重渲染 vs 已提交,逐语言   |
| 2   | 生成器**悄悄漏掉** schema | 产物少几个模型,而文件看起来正常              | **覆盖断言**:逐 schema 数**出口**      |
| 3   | 生成器把**类型映射错**    | `integer` 渲染成 `String`,编译得过、运行时炸 | **映射断言**:契约类型 → 目标类型,逐条  |
| 4   | 生成器输出**语法不合法**  | 产物根本编译不过                             | 🚨 **需要编译器 —— 见 §四,当前是缺口** |

⚠️ **第 1 条是唯一被现有机制覆盖过的**(V0.5.0 期间真的抓到过一次)。
第 2、3 条此前**连 TS SDK 都没有**;第 4 条对 TS 由 `typecheck` 覆盖,
而 Kotlin / Swift 没有。

⇒ **同一个漏洞面从一种语言变成三种,防线也必须逐语言各有一份。**
「只验 TS 那条」在结构上就不成立:它证明的是 TS 的渲染器会红,
与 Kotlin 的渲染器会不会红**没有任何关系**。

---

## 二、裁决:手写 Node 渲染器

### 选项与代价

| 方案                        | 代价                                                                     |
| --------------------------- | ------------------------------------------------------------------------ |
| **openapi-generator**(Java) | 见下 —— 三条,第一条是决定性的                                            |
| **手写 Node 渲染器**(选中)  | 要自己维护映射;但契约只有 44 个 schema,**其中 42 个是平凡 object**(实测) |

### 为什么不用 openapi-generator(它其实跑得起来)

实测:`npx @openapitools/openapi-generator-cli` 能装上并运行(本机 Java 17)。
**能跑不是选它的理由** —— 三条反对:

1. ★ **同步断言会变成一次 JVM 子进程调用。**
   现有模式是 `render(document) → string` 的**纯函数**,生成脚本与校验测试
   **共用同一条代码路径** —— 这一点是那条断言成立的前提(两条路径哪怕差一个
   换行,校验就永远红或永远绿)。换成外部进程之后:每跑一次测试起一次 JVM,
   而且校验的是「子进程的输出」而不是「生成时用的那段逻辑」。
2. **生成器自身的版本会改变输出。** 那条同步断言会在**升级生成器**时变红 ——
   而那种红与「契约改了没重生成」在输出上一模一样。一条会因无关原因变红的
   断言,会训练人去忽略它。
3. **CI 要多一个 Java 工具链**,而本仓的门禁脚本刻意零依赖。

⚠️ **反过来说**:契约若长到几百个 schema、或要覆盖 oneOf/allOf 的复杂组合,
这笔账会翻过来。**判据是「维护映射的成本 vs 维护外部生成器的成本」**,
不是「手写更纯粹」。现在的实测数据(42/44 是平凡 object)支持手写;
数据变了就该重新算。

## 三、不变式:`render(document) → string` 是纯函数,两处共用

```
packages/api-contract/openapi.json
        │
        ├── sdk/typescript/scripts/render.ts   renderSchema()
        ├── sdk/kotlin/scripts/render.ts       renderKotlin()
        └── sdk/swift/scripts/render.ts        renderSwift()
                 │                    │
        generate.ts(写盘)      generated.test.ts(重渲染并比对)
```

**生成脚本与校验测试必须调同一个函数。** 各写一份的话,校验的是
「两份实现是否一致」,而不是「产物是否最新」。

---

## 四、🚨 已知缺口:生成产物的**语法合法性**无人验证

**实测**:本机与 CI 的 `ubuntu-latest` 都**没有 `kotlinc` 与 `swift`**
(Java 17 有,但 Java ≠ Kotlin)。

| 语言   | 语法合法性谁验证              |
| ------ | ----------------------------- |
| TS     | ✅ `pnpm typecheck`(已有门禁) |
| Kotlin | ❌ **无人** —— 缺口           |
| Swift  | ❌ **无人** —— 缺口           |

⇒ **一个会生成非法 Kotlin 的渲染器,能通过本版本的全部断言。**

**为什么仍然先做**:同步 / 覆盖 / 映射三道断言各自防住的是不同的坏法,
它们不因第四道缺席而失效。**明写缺口比假装完整好** ——
后者会让下一个人以为「绿了 = 产物能编译」。

**补法(未做,记录规格)**:CI 加两个 job,分别用
`actions/setup-java` + Kotlin 编译器、以及 `swift-actions/setup-swift`
编译**示例工程**(示例编译得过 ⇒ SDK 语法合法)。

⚠️ 按本仓新规,CI job 必须在守卫计数里登记并有负向验证 ——
所以补这两个 job 时要连同 `CI_JOB_VERIFICATION` 一起加,不能只加 job。
本版本不做,是因为**本机没有这两个编译器,加了也验不了它会不会红**,
而「加一个自己没见过它红过的检查」正是本仓反复警告的形状。
