# 控制平面的仓库分工

> 主仓 `dshwar` 与控制平面仓 `dshwar-console` 之间,什么放哪一边。
> 定于 V0.5.0(D1),`dshwar-console` 目前是**空占位**。

## 一句话

> **契约在主仓,服务在独立仓,前端暂在主仓。**

## 分工表

| 东西                                                      | 放哪                       | 为什么                                                                                                       |
| --------------------------------------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **`@dshwar/console-contract`** —— 共享类型与 OpenAPI 契约 | 🏠 **主仓**                | 它引用运行时平面的概念(principal / 租户 / 配额 / 用量),**必须与运行时版本联动**。放主仓才被 `check:all` 覆盖 |
| **控制台服务本体** —— API server + 数据库 + 迁移          | 📦 **`dshwar-console`**    | 与 dsh 运行时**零耦合**。它有自己的数据库、自己的部署周期、自己的伸缩特性                                    |
| **控制台前端** —— React                                   | 🏠 **主仓 `console-web/`** | ⚠️ 见下方「前端为什么暂在主仓」                                                                              |
| **`billing-hosted`**、托管服务                            | 📦 闭源,独立               | CLAUDE.md 第八节                                                                                             |

## 契约为什么必须在主仓

放独立仓的话,那一整套门禁要**复制一份**:契约冻结、版本一致性、类型检查、
开源纯净度。而**复制出来的第二份清单迟早会漂** —— 这不是假想,
V0.4.7 首次 CI 复盘查出的根因正是「本地 `check:all` 与 `ci.yml` 是两份清单」。

同一个道理:**与其守住两份清单同步,不如只留一份。**

## 前端为什么暂在主仓

这是执行期的自主决策(见 [`DECISIONS/AUTOPILOT-LOG.md`](DECISIONS/AUTOPILOT-LOG.md) A1),
理由是 **D7 的三条前端约束要加守卫,而守卫不能建在空集上**:

- 扫描一个不存在的目录 → 永远绿
- 而「一条永远绿的检查与没有检查等价,但更危险」是本仓反复强调的

要让那三条守卫的负向验证有意义,被检查的对象必须真实存在。

⚠️ **将来搬到 `dshwar-console` 时,守卫必须一起搬。**
留在主仓的守卫会退化成空集扫描,又变回永远绿 —— 那比没有守卫更糟。

## 依赖方向(单向,不得反转)

```
dshwar-console  ──依赖──▶  @dshwar/console-contract  (npm)
                ──依赖──▶  @dshwar/sdk               (npm)

dshwar (主仓)   ──不依赖──  dshwar-console
```

**主仓永远不依赖控制平面。** 这条是硬的:运行时能不能跑,不该取决于
控制台在不在。一个只装了运行时的自建者,应该拿到一个完整可用的系统 ——
那正是开源边界声明里承诺的「可用的完整基座」。

## `dshwar-console` 建仓时要带的东西

按主仓已经踩过的坑,建仓第一天就该有(而不是等它咬人):

1. `check:all` 单入口 —— **CI 只调它一个**,不枚举门禁(V0.4.7 的教训)
2. 版本一致性守卫 —— 与主仓的 `console-contract` 版本必须对得上
3. 守卫的负向验证 —— 新增检查必须证明它会红
4. 元规则:每新增一个验证机制,回答「谁验证它?」(CLAUDE.md 第六节)

⚠️ **不要把主仓的 `scripts/` 整个复制过去。** 那些守卫大半是针对
运行时平面的约束(上游深链、锁版、凭据泄漏、principal 消费方),
控制平面根本没有那些概念。**复制一份用不上的守卫,只会训练人去忽略它们。**
