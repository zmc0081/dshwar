# 可行性报告 V0.4.5 —— 跨进程驱动

> **结论:可行,进程隔离继续做。** 五条验证中 A/B/C/D 全绿,E 本次不测(理由见 §5)。
> 关键结论是**验证 C 的手段 a 可行** —— 取消语义不会因为进程隔离而退化,红线 3 保得住。
>
> 测量环境:Windows 11 Pro 26200 · Node 22 · pnpm 11 · 上游 `0.1.0-rc.6`
> 日期:2026-08-16 · 对应 Session:M0.4.5 Session 0(止损点)

## 这份报告要回答的问题

V0.4.5 压在一条**未验证的假设**上:

> 网关能在子进程里驱动 agent,并把流式事件完整拿回来。

V0.2.0 Session 0 验证的是**进程内**驱动 —— 跨进程是另一回事。若事件回传做不到,
整版必须改成弱化形态(只隔离文件系统与凭据,仍在父进程驱动)或推迟。

## 验证方式:落成常驻契约测试,而不是一次性脚本

沿用 V0.4.0 Session 0 的做法。验证代码在
[cross-process.test.ts](adapters/dsh-0.1.0/test/cross-process.test.ts) +
[child-agent.mjs](adapters/dsh-0.1.0/test/fixtures/child-agent.mjs),
跟着 `pnpm test` 每次跑。**上游哪天改掉事件词表或 cancel 语义,跟版时它先红**,
而不是等到 supervisor 上线后在生产里发现。

子进程装配 `gateway/src/runtime.ts` 里 `GATEWAY_PLUGINS` 的**全部 11 个插件**,
顺序与之一致(含 `fs-tenant` 包 `fs-local` 的那层嵌套)。
刻意不图省事只装上游核心 6 个 —— 少装 4 个量出来的数字偏乐观,
而 §6 的数字会被 Session 4 的部署文档引用,采用者据此做容量规划。

## 1. 验证 A —— 子进程能起来并装配 ✅

| 断言                     | 结果          |
| ------------------------ | ------------- |
| 子进程完成 11 插件装配   | ✅            |
| principal 经 IPC 传入    | ✅            |
| 冷启动耗时可测           | ✅ 见 §6      |
| 装配失败时错误报回父进程 | ✅ 不静默死掉 |

实测输出:

```
[验证 A] 冷启动 128 ms(其中插件装配 14 ms),常驻 58 MB
```

**一处方法上的坑,记下来免得下次再踩。** 最初把冷启动写成子进程内的
`Date.now() - t0`(`t0` 取自模块体顶部),量出来 **10 ms** —— 这个数是错的。
ESM 的 import 在模块体执行**之前**就求值完了,所以它只包含插件装配,
不含进程创建、Node 引导与模块加载。真正的冷启动必须由**父进程侧**的墙钟测量
(`fork()` → 收到 `ready`),量出来是 **115–128 ms**,**十倍之差**。

报告里两个数分开列:`冷启动`(父进程墙钟,采用者关心的)与
`插件装配`(子进程自报,定位瓶颈用的)。

### 顺带确认:进程边界确实隔断状态

两个子进程各自从 0 起算 seq,序列完全相同 —— 若是同一进程内的两个会话,
第二个的 seq 会接着第一个往上走。这是 R1「一 principal 一进程」的前提,
但**进程池编排本身是 Session 1 的事**,这里只证明边界成立。

## 2. 验证 B —— 流式事件完整回传 ✅

**这是止损判据所在的一条。全绿。**

| 断言                                                                   | 结果 |
| ---------------------------------------------------------------------- | ---- |
| 事件词表与进程内一致                                                   | ✅   |
| `turn/start` `assistant/chunk` `assistant/message` `turn/end` 四类齐全 | ✅   |
| seq 单调不回退                                                         | ✅   |
| 文本增量逐字回传,不丢不乱序                                            | ✅   |
| 用量随 `assistant/message` 回传                                        | ✅   |

seq 单调这一条不是锦上添花:**SSE 的 `Last-Event-ID` 续传依赖它**。
跨进程之后若 seq 由子进程各自生成而父进程直接透传,多进程混流会撞号 ——
Session 2 做事件回传时,**seq 的权威必须留在父进程的会话簿**,
子进程的 seq 只作进程内序。这一条写进 Session 2 的任务书。

用量能回传意味着**计量在跨进程下仍有输入**(R7 的前提)。上游把用量挂在
`assistant/message` 上而非单独的 usage 记录 —— 这一点与 V0.4.0 的实测一致,
跨进程没有改变它。

## 3. 验证 C —— 取消 ★ 本版本的代价 ✅

> 路线图曾把「解决无 cancel」列为 supervisor 的收益。**那是反的。**
> 进程内的 `Agent.cancel(cause)` 早在 V0.2.0 就实测可用,
> `DELETE /v1/sessions/{id}` 从那时起就能截断输出。
> **进程隔离是把一个已经好用的东西变成需要重新解决的问题。**
> 这一节验证它能被解决。

| 手段                              | 可行 | 代价                               |
| --------------------------------- | ---- | ---------------------------------- |
| **a. IPC 发指令 + 进程内 cancel** | ✅   | **无** —— 推荐                     |
| b. SIGTERM                        | ✅   | 本轮已产出的输出全丢,无 `turn/end` |
| c. SIGKILL                        | ✅   | 同上,且没有任何收尾机会            |

实测输出:

```
[验证 C-a] IPC 取消:收到 4/40 个增量后截断
```

**手段 a 可行,红线 3 保得住。** 路径是:父进程收到 `DELETE` → IPC 送 `cancel`
→ 子进程调进程内的 `agent.cancel({ kind: 'user' })` → 上游把 `AbortSignal`
传到适配器 → 流真的停。40 个增量只收到 4 个,截断是真的,不是接口返回了 200。

b/c 也能停,但**它们停的是进程不是这一轮** —— 该进程上的其他会话陪葬,
且客户端拿不到 `turn/end`。所以 Session 2 的实现顺序是:
**a 为正路,b 作为 a 超时后的兜底,c 作为 b 超时后的最后手段。**
三级降级的超时值留给 Session 1 的进程池配置。

## 4. 验证 D —— 崩溃可观测 ✅

子进程 `process.exit(7)` 后,父进程从 `exit` 事件拿到退出码 `7`。
区分「正常结束」与「崩溃」靠退出码,这是 R5 崩溃恢复的前提:
**子进程死亡 → 该进程上的全部会话标记失败 → SSE 发 error 事件后关闭。**

配合验证 C 的 b/c(信号退出时 `signal` 非空、`exitCode` 为空),
父进程能区分三种终止:正常结束 / 主动杀死 / 崩溃。三者在审计里应当是不同的事件。

## 5. 验证 E —— node-pty 两层嵌套 ⬜ 本次不测

**理由,不是遗漏:** `@deepseek-ai/dsh-subprocess-local` 当前未安装。
`gateway/src/runtime.ts` 的 `DELIBERATELY_OMITTED` 里写明了原因 ——
它依赖 node-pty 原生构建,且上游 `ProcessInspector` 只实现 linux / darwin,
**win32 直接抛错**(`docs/FEASIBILITY-REPORT.md` 验证 D)。

V0.1.0 验证 D 已证明 node-pty 在**外部拉起的子进程**里可用。本版本再套一层
是否仍成立,要等 subprocess 真被装进 supervisor 拉起的进程时才有意义 ——
**现在测等于测一个还不存在的装配。**

**记入待测清单:Session 1 装配 supervisor 子进程时补测,Linux 与 Windows 各一次。**
Windows 的退化行为(ProcessInspector 抛错)要在 Session 4 的部署文档里写明。

### Session 1 补记:切开来测了能测的那一半

验证 E 里有两件风险不对等的事,Session 1 把它们分开处理:

| 子问题                                    | 谁的风险      | 状态                                                |
| ----------------------------------------- | ------------- | --------------------------------------------------- |
| supervisor 的子进程还能不能**再拉起进程** | supervisor 的 | ✅ 已测(`packages/supervisor/test/process.test.ts`) |
| node-pty 的**原生绑定**在深度 2 是否工作  | node-pty 的   | ⬜ 仍未测                                           |

第一条是 supervisor 可能破坏的 —— IPC 通道、stdio 继承、句柄传递都在它的影响范围内。
已用一条真进程测试钉住:子进程 spawn 孙进程,拿回 stdout 与退出码。**agent 的
shell 工具依赖的正是这个**;它若不成立,进程隔离下 agent 就没有执行能力,这一版白做。

第二条 supervisor 碰不到,且 V0.1.0 验证 D 已证明深度 1 可用。
**残余风险由 Session 3 装上 subprocess 之后补测。**

## 6. 进程隔离的代价 —— 给容量规划用的数字

五次采样(同一台机器,冷缓存后连续跑):

| 次  | 冷启动(父进程墙钟) | 插件装配(子进程自报) | 常驻 RSS |
| --- | ------------------ | -------------------- | -------- |
| 1   | 128 ms             | 14 ms                | 58 MB    |
| 2   | 118 ms             | 12 ms                | 57 MB    |
| 3   | 115 ms             | 13 ms                | 58 MB    |
| 4   | 115 ms             | 13 ms                | 58 MB    |
| 5   | 115 ms             | 13 ms                | 57 MB    |

**读法:**

- **冷启动 ~115 ms。** 其中插件装配只占 13 ms —— **九成时间花在进程创建与模块加载上**。
  这意味着优化装配代码没什么用,要压只能压进程复用率(所以 R1 是「一 principal
  一进程」而非「一会话一进程」——后者是数量级的差别)。
- **常驻 ~58 MB。** 单机 100 个活跃 principal ≈ **5.8 GB** 常驻。
  这个数决定了 Session 1 的「单机进程上限」不是可选配置而是必需项,
  也决定了空闲回收的默认值不能太长。
- 这些数字**只含运行时平面**。子进程不装 policy / metering / audit
  (判定留在父进程,见 R7),所以不会再往上涨太多。

⚠️ **数字来自 Windows 开发机,不是生产基线。** Linux 上的 fork 更便宜,
预期冷启动更低。Session 4 写部署文档前应在 Linux 上重测一遍。

## 7. 对任务书的影响

止损判据是「**若事件无法完整回传**,改弱化形态或整版推迟」。
验证 B 全绿,**不触发止损,V0.4.5 按原计划推进**。

三条要带进后续 Session 的结论:

1. **Session 1** —— 进程上限是必需项(58 MB/进程);空闲回收默认值要保守;
   补测验证 E(node-pty 两层嵌套,Linux + Windows)。
2. **Session 2** —— 取消实现走「a 为正路 → b 兜底 → c 最后手段」的三级降级;
   **seq 的权威留在父进程会话簿**,子进程 seq 只作进程内序。
3. **Session 4** —— §6 的数字要在 Linux 上重测后才写进部署文档;
   Windows 的 ProcessInspector 退化行为要写明。
