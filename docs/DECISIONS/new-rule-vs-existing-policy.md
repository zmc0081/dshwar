# 新规则落地时必须核对既有规则

日期:2026-08-21(V0.8.0)· 状态:✅ 已机制化

> **形状**:仓库里同时存在两条规则,对**同一件事**给出相反的答案。
> 而后加的那条是错的 —— 因为加它的时候没有人去核对既有的那条。
>
> **它不是「规则写错了」。** 规则本身的逻辑是自洽的、注释是讲得通的;
> 错的是它与一条**早已存在并且写明了理由**的策略冲突,而落地时没人核对。

---

## 实例:`schema.variant.added`

V0.8.0 给契约冻结检查补 `anyOf` / `oneOf` 维度时,`diffUnion` 的第一版
把「联合的分支集合变了」**一律**判成破坏性 —— 包括**多**一个分支。

而同一件事在枚举上早有裁决。`packages/api-contract/src/common.ts:19-31`:

> ## ⚠️ 客户端必须优雅处理未知枚举值(V0.4.6 起,契约级要求)
>
> 本枚举**会在 v1 内追加新值**。任何消费方在 `switch` 上必须有 `default` 分支……
> **同样的要求适用于 `StreamEventType` 与其余所有闭集枚举。**

`StreamEventType` 正是 SSE 事件的词表,而 `StreamEvent` 那个 `oneOf` 就是它的
结构版本。于是:

|                                       | 加一个成员 | 依据                                                  |
| ------------------------------------- | ---------- | ----------------------------------------------------- |
| `enum.value.added`(V0.4.6)            | **相容**   | common.ts 的契约级要求,且**点名**覆盖 StreamEventType |
| `schema.variant.added`(V0.8.0 第一版) | **破坏**   | 无 —— 只是「分支集合变了」的一个自然推论              |

⇒ **给 SSE 加一个事件类型会被契约冻结检查拦住** —— 而那正是 V0.4.6
放宽 `enum.value.added` 时点名要允许的演进。

### 它差点没被发现

第一轮的 15 例探针里没有「加一个 SSE 事件类型」这一例 ——
因为那一轮的清单是照着**已知漏报**列的,而这是个**误报**。
它是第二轮探针(照判官提出的「还剩什么没补」重列)才撞出来的。

⇒ 顺带的一条:**补漏报的探针清单,天然不覆盖误报。**
每一轮都要各留几条「这一定不能红」的反向对照。

## 裁决:把核对变成一条会红的断言

修好这一次只值一次。真正的要求是:

> **新增 `ContractChangeCode` 时,必须核对它与既有码、
> 以及 `common.ts` 里明写的策略是否冲突。**

而「必须核对」如果只是一句话,下一次照样会忘。所以它落成了机制:

### 机制:同一族的分类码必须同向

`packages/api-contract/test/freeze.test.ts` 的「策略一致性」一节。

| 族                 | 成员                                                                                        | 断言              |
| ------------------ | ------------------------------------------------------------------------------------------- | ----------------- |
| **闭集加一个成员** | `enum.value.added` · `schema.variant.added` · `response.added` · `media.type.added`         | 全部必须 **相容** |
| **闭集删一个成员** | `enum.value.removed` · `schema.variant.removed` · `response.removed` · `media.type.removed` | 全部必须 **破坏** |

族内任何一条与其余不同向 → 测试红,并在失败信息里指回 common.ts 的原文。

**两条成对**:只验「加值放行」的话,一个什么都放行的实现照样全绿。
两条各自都数出口(`expect(asserted).toBe(...)`),且每条变异前先断言
「文档真的变了」—— 否则一个 no-op 变异会冒充通过。

**负向验证**(已跑):把 `schema.variant.added` 改回 `breaking`,
测试立刻红,失败信息是
「这些「加一个成员」被判成了破坏性,而同族的 enum.value.added 是相容的」。

## 落到操作上

新增一个分类码时,除了 CLAUDE.md 第六节要求的「一条独立负向验证 + 完备性断言」,
再回答一个问题:

> **「这个码判的这件事,仓库里有没有别的码也在判?两边同向吗?」**

答法不是回忆,是**去找**:在 `CONTRACT_CHANGE_CODES` 里扫同后缀的
(`.added` / `.removed` / `.changed`),以及在 `common.ts` 与
`freeze.ts` 的注释里搜「契约级」「V0.4.6」这类**写明了理由**的段落。

⚠️ 写明了理由的旧注释,权重高于新写的推论。
`enum.value.added` 那段注释里有一句话直接适用:

> **改判据必须连理由一起改。**

反过来也成立:**新加的判据要先去找有没有一条既有的理由已经管着它了。**
