# 设计系统与 branding 契约:同一份契约的两个副本,**无自动同步**

日期:2026-08-18 · 状态:约定(V0.8.0 回写时确立)

> **一句话**:Claude Design 里名为 **DSHWAR** 的设计系统,与
> `packages/console-contract/src/branding.ts`,是**同一份契约的两个副本**。
> 两者之间**没有任何自动同步**。改一边必须同步改另一边。

---

## 一、为什么会有两个副本

它们服务的是同一个决定(「哪些内容可被租户替换」),但**落点不同**:

|          | 设计系统(Claude Design · DSHWAR)     | `branding.ts`(本仓)                         |
| -------- | ------------------------------------ | ------------------------------------------- |
| 是什么   | 令牌、色阶派生、角色令牌、对比度规则 | 配置契约的**形状**:字段、类型、可空性       |
| 谁消费   | 设计稿、组件库、视觉走查             | 控制平面 API、控制台前端、V0.7.0 客户端     |
| 派生算法 | ✅ 在这边                            | ❌ **刻意不在**(见 `branding-variables.md`) |

**这不是重复,是分工。** 色阶不进契约是明确裁决 ——
放进去就等于允许两端各派生一套,而那两套迟早会不一样。

> ### ⊕ 2026-08-22(V0.9.0)细化,**不是推翻上表**
>
> 上表那句「派生算法 ❌ 刻意不在」说的是**不在契约包**。V0.9.0 移植设计 kit 时
> 细化为:**算法在 `packages/design-system`(实现包),契约包只有形状。**
>
> 为什么要细化:`branding-variables.md` 同时要求「色阶由**客户端**派生」——
> 客户端要派生,算法就必须在仓库里。上表原文没有区分「不在契约包」与
> 「不在仓库」,照字面读会得出「仓库里不能有派生实现」,而那与客户端派生冲突。
>
> 为什么放实现包而不是契约包:**契约包的价值在于稳定** ——
> 它被三种 SDK 生成器读、被契约冻结检查盯、被跨包 import;
> 而派生算法会随对比度规则调整而变。把会变的东西放进必须稳的包,迟早要拆。
>
> 落点:`packages/design-system/src/accent/derive.ts`,是
> `tokens/derive-accent.js` 的**逐字移植**(只改类型,不改数值与控制流)。

⚠️ 但分工的代价是:**同一个事实被写了两遍**,而两遍之间没有机器盯着。

---

## 二、约定

> **branding 契约的任何改动,必须同步更新设计系统;反之亦然。**

具体到「什么算改动」:

| 改了什么                                           | 必须同步吗                  |
| -------------------------------------------------- | --------------------------- |
| 增删字段                                           | ✅ 必须                     |
| 改字段类型或可空性(如 `string` → `string \| null`) | ✅ **必须** —— 见 §三的实例 |
| 改默认值 / 建议值                                  | ✅ 必须                     |
| 改校验下限(对比度阈值、重打光带边界)               | ✅ 必须                     |
| 改注释措辞而不改语义                               | ❌ 不必                     |

`branding.ts` 顶部有一行注释指向本文,免得改的人不知道还有另一半。

### ⊕ 待同步回设计侧的清单(V0.9.0 Session 1 起)

移植 kit 时撞到的、**仓库这边已经定了而设计侧还没改**的事。
设计系统在 Claude Design 里,本仓改不到它 —— 所以记在这里,
下次动设计系统时一并改掉。

| #   | 设计侧要改什么                                                                    | 为什么                                                                                                                                                                                                                                                                                  |
| --- | --------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `QuotaBar.d.ts` 与 `QuotaBar.prompt.md` 里的「填充恒为 n-700 / 填充色写死 n-700」 | **与 `QuotaBar.jsx` 自己的注释矛盾**,而那条注释是对的:「06 的规则是填充**不得是 accent**,不是**必须是 n-700 字面值**」。n-700 在暗主题下不反转,写死会让暗主题的填充糊在底色上。仓库侧取 `--text-secondary`(亮 = n-700 / 暗 = n-400)。⇒ **文档写的是字面,实现执行的是意图,以实现为准。** |
| 2   | `Wordmark.jsx` 的 `size = cjk ? 15 : 15`                                          | **三元两支同值**。留着会让下一个人以为其中一支该改。仓库侧落成单一值并注明「两种字集都验过,结论一致」。                                                                                                                                                                                 |
| 3   | 字号阶梯缺令牌:16px(CJK 基准)与 15px(shrink 末档)                                 | 阶梯的第一档用了 `--fs-wordmark`,后两档是字面值 —— **一条阶梯劈在两个来源上**,改令牌只动得了第一档。仓库侧补了 `--fs-wordmark-cjk` / `--fs-wordmark-shrink`。⚠️ `--ls-wordmark-cjk` 的原注释里本来就写着「字号降至 16px」:那个数一直是规范的一部分,只是没有名字。                       |
| 4   | `Metric` 的 `SIZES` 末级 `['var(--fs-body-lg)', '1.25', '0']`                     | 前三级用令牌、末级用字面。而 `--lh-body-lg` 是 **1.6**,与 1.25 不是同一个值的两种写法。仓库侧补了 `--lh-metric-tight` / `--ls-metric-tight`(收紧是刻意的:那一档专供「数字长到撑不下」时用)。                                                                                            |
| 5   | `LogoSlot.jsx` 的 `srcDark \|\| src`                                              | 应为 `??`,与 `logoFor()` 及 `LogoSlot.prompt.md` 的文字描述一致。`\|\|` 把空串也当缺失 —— 而空串是**配置错误**,不是没配,悄悄回落等于替客户把错配当成没配。                                                                                                                              |
| 6   | `Checkbox.jsx` 的方块没有 `tabIndex` / `onKeyDown`                                | **键盘完全够不到**。`role="checkbox"` 的 span 对读屏是复选框、对键盘是死文字。仓库侧补了 `tabIndex` + 空格/回车 + `:focus-visible` 焦点环。                                                                                                                                             |
| 7   | `CodeRef.jsx` 的复制回执                                                          | `setDone(true)` 在 try 外,且 `writeText` 是 Promise、**同步 catch 捕不到它的拒绝** —— 于是最常见的失败路径(权限、非安全上下文)会给出**假的成功回执**。仓库侧改成等 Promise 落定,失败翻 x 并转 danger 色。                                                                               |

⚠️ **1 / 5 / 6 / 7 是设计侧的缺陷,不是口味差异** —— 它们在设计稿里也是错的,
不改的话下一个照着 kit 写新组件的人会把同样的洞再造一遍。

## 三、实例:V0.8.0 的回写就是没同步的产物

设计侧核对时发现**两处**,都是「契约这边写下的东西,与设计侧的规则对不上」:

### ① 默认主色命中了契约自己禁止的分支

契约的 `NEUTRAL_BRANDING.primaryColor` 是 `#2F6FEB`,而设计侧的派生规则规定:
实心填充若落在中亮带 `L ∈ (0.55, 0.80)` 就要**重打光(RE-LIT)**。

**实测**(本仓 `test/branding.test.ts` 独立复算,与设计侧一致):

|                   | L         | C     | H      | 派生策略               |
| ----------------- | --------- | ----- | ------ | ---------------------- |
| `#2F6FEB`(旧默认) | **0.573** | 0.199 | 261.8° | 🚨 **带内 → RE-LIT**   |
| `#1D5BD4`(新建议) | **0.509** | 0.197 | 261.9° | ✅ 带外 → **VERBATIM** |

⇒ **契约一边要求「带内要阻塞确认」,一边把一个带内的值设成默认。**
后果是那条确认流程**在默认路径上永远走不到** —— 半条死代码。

新值取自旧默认色所派生 ramp 的 **700 档**:色相漂移 **0.1°**、彩度贴近,
观感上是同一个蓝,只是压暗到带外。

### ② 默认值冒充「未配置」

`primaryColor` 原本是 `string`,用 `#2F6FEB` 这个哨兵值表示「没配」。
与 V0.6.0 的发票卖方字段**同形**:「未配置」与「配置成某个值」必须在
**类型层**可分,靠哨兵值区分是一条**运行时约定** ——
而运行时约定会被下一个人当成普通值,他没有理由知道 `#2F6FEB` 有特殊含义。

⇒ 改为 `string | null`,`null` = 未配置 = 中性外观(无彩)。

## 四、这条约定的已知弱点(明写)

**它靠人执行,没有机器盯着。** 本仓能做的只有半边:

| 能自动查的(本仓已做)                                    | 查不到的                   |
| ------------------------------------------------------- | -------------------------- |
| 建议色是否落在带外(`test/branding.test.ts`)             | 设计侧改了带边界而契约没跟 |
| `primaryColor` 的 null 是否被兜底掉(`check-guards.mjs`) | 设计侧增删了角色令牌       |
| 中性外观里是否混进了默认值                              | 设计侧改了对比度下限       |

⚠️ **右边那一列目前无人看着。** 写在这里不是为了心安,是为了让下一个
撞见不一致的人知道:**那不是 bug,是这条约定的已知边界** ——
以及,若不一致反复发生,该做的是把规则搬到一处、而不是再加一遍人工检查。

**判据**:同一处不一致出现**第二次**时,就该考虑让设计侧的规则成为可导出的
数据(例如一份 tokens JSON),由契约侧读取并断言 —— 那时「两个副本」
才真正变回「一份事实」。现在只出现了一次(V0.8.0 这次),还不值得。

> ### 🚨 上面这条判据已于 2026-08-22(V0.9.0)**判定失效**。原文保留在上面。
>
> **保留它不是存档癖 —— 它是一次判断失误的记录,而记录比结论有用。**
>
> 失效的理由不是「后来变得值得做了」,是**这条判据的前提不成立**:
>
> 「等第二次」隐含着「第一次会被发现」。而**同一段文字自己**列的三项
> (带边界改了 / 角色令牌增删 / 对比度下限改了)紧接着写明**目前无人看着** ——
> 不一致出现第一次时不会有人知道,于是「出现第二次」这个条件
> **永远不会被满足**。
>
> ⇒ 一条永远等不到触发条件的判据,与没有判据等价 ——
> 而它比没有判据更糟:它让人以为有一个会响的闹钟。
>
> **已做的替代**:三项规则做成可导出数据
> `packages/design-system/src/accent/spec.ts`,由
> `packages/design-system/test/accent.test.ts` 的三条断言盯着 ——
>
> | 断言                                 | 绑住上表哪一项「查不到的」 |
> | ------------------------------------ | -------------------------- |
> | ① 九个固定种子都满足契约三条下界     | 设计侧改了对比度下限       |
> | ② 演示种子的六个令牌逐字节等于设计卡 | 设计侧增删了角色令牌       |
> | ③ 带内必 RE-LIT、带外必 VERBATIM     | 设计侧改了带边界           |
>
> ⚠️ 种子表**固定不随机**:随机会让失败不可复现,而一条不可复现的红
> 与一条恒绿的检查一样没用。表里 4 个带内、5 个带外 ——
> 全带外的话,一个「永远 VERBATIM」的实现照样全绿。
>
> ⇒ **顺带记一条更一般的教训**:凡是「等它再发生一次就动手」的判据,
> 先问一句「**第一次发生时,谁会知道?**」。答不上来的,那条判据就是死的。
