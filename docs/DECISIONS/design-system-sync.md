# 设计系统与 branding 契约:同一份契约的两个副本,**无自动同步**

日期:2026-08-18 · 状态:约定(V0.8.0 回写时确立)

> **一句话**:Claude Design 里名为 **DSHWAR** 的设计系统,与
> `packages/console-contract/src/branding.ts`,是**同一份契约的两个副本**。
> 两者之间**没有任何自动同步**。改一边必须同步改另一边。

---

## 一、为什么会有两个副本

它们服务的是同一个决定(「哪些内容可被租户替换」),但**落点不同**:

|          | 设计系统(Claude Design · DSHWAR)     | `branding.ts`(本仓)                         |
| -------- | ------------------------------------ | ------------------------------------------- |
| 是什么   | 令牌、色阶派生、角色令牌、对比度规则 | 配置契约的**形状**:字段、类型、可空性       |
| 谁消费   | 设计稿、组件库、视觉走查             | 控制平面 API、控制台前端、V0.7.0 客户端     |
| 派生算法 | ✅ 在这边                            | ❌ **刻意不在**(见 `branding-variables.md`) |

**这不是重复,是分工。** 色阶不进契约是明确裁决 ——
放进去就等于允许两端各派生一套,而那两套迟早会不一样。

⚠️ 但分工的代价是:**同一个事实被写了两遍**,而两遍之间没有机器盯着。

---

## 二、约定

> **branding 契约的任何改动,必须同步更新设计系统;反之亦然。**

具体到「什么算改动」:

| 改了什么                                           | 必须同步吗                  |
| -------------------------------------------------- | --------------------------- |
| 增删字段                                           | ✅ 必须                     |
| 改字段类型或可空性(如 `string` → `string \| null`) | ✅ **必须** —— 见 §三的实例 |
| 改默认值 / 建议值                                  | ✅ 必须                     |
| 改校验下限(对比度阈值、重打光带边界)               | ✅ 必须                     |
| 改注释措辞而不改语义                               | ❌ 不必                     |

`branding.ts` 顶部有一行注释指向本文,免得改的人不知道还有另一半。

---

## 三、实例:V0.8.0 的回写就是没同步的产物

设计侧核对时发现**两处**,都是「契约这边写下的东西,与设计侧的规则对不上」:

### ① 默认主色命中了契约自己禁止的分支

契约的 `NEUTRAL_BRANDING.primaryColor` 是 `#2F6FEB`,而设计侧的派生规则规定:
实心填充若落在中亮带 `L ∈ (0.55, 0.80)` 就要**重打光(RE-LIT)**。

**实测**(本仓 `test/branding.test.ts` 独立复算,与设计侧一致):

|                   | L         | C     | H      | 派生策略               |
| ----------------- | --------- | ----- | ------ | ---------------------- |
| `#2F6FEB`(旧默认) | **0.573** | 0.199 | 261.8° | 🚨 **带内 → RE-LIT**   |
| `#1D5BD4`(新建议) | **0.509** | 0.197 | 261.9° | ✅ 带外 → **VERBATIM** |

⇒ **契约一边要求「带内要阻塞确认」,一边把一个带内的值设成默认。**
后果是那条确认流程**在默认路径上永远走不到** —— 半条死代码。

新值取自旧默认色所派生 ramp 的 **700 档**:色相漂移 **0.1°**、彩度贴近,
观感上是同一个蓝,只是压暗到带外。

### ② 默认值冒充「未配置」

`primaryColor` 原本是 `string`,用 `#2F6FEB` 这个哨兵值表示「没配」。
与 V0.6.0 的发票卖方字段**同形**:「未配置」与「配置成某个值」必须在
**类型层**可分,靠哨兵值区分是一条**运行时约定** ——
而运行时约定会被下一个人当成普通值,他没有理由知道 `#2F6FEB` 有特殊含义。

⇒ 改为 `string | null`,`null` = 未配置 = 中性外观(无彩)。

---

## 四、这条约定的已知弱点(明写)

**它靠人执行,没有机器盯着。** 本仓能做的只有半边:

| 能自动查的(本仓已做)                                    | 查不到的                   |
| ------------------------------------------------------- | -------------------------- |
| 建议色是否落在带外(`test/branding.test.ts`)             | 设计侧改了带边界而契约没跟 |
| `primaryColor` 的 null 是否被兜底掉(`check-guards.mjs`) | 设计侧增删了角色令牌       |
| 中性外观里是否混进了默认值                              | 设计侧改了对比度下限       |

⚠️ **右边那一列目前无人看着。** 写在这里不是为了心安,是为了让下一个
撞见不一致的人知道:**那不是 bug,是这条约定的已知边界** ——
以及,若不一致反复发生,该做的是把规则搬到一处、而不是再加一遍人工检查。

**判据**:同一处不一致出现**第二次**时,就该考虑让设计侧的规则成为可导出的
数据(例如一份 tokens JSON),由契约侧读取并断言 —— 那时「两个副本」
才真正变回「一份事实」。现在只出现了一次(V0.8.0 这次),还不值得。
