# 决策:守卫脚本不得修改仓库

> **状态**:✅ 已生效并接入守卫(V0.4.7,2026-08-16)。
> 起因是一次真实事故 —— 一个用来保证纪律的脚本把契约文件改坏了,**而且没说**。

## 事故

`pnpm check:all` 跑到 `verify-guards` 时,还原 `packages/api-contract/openapi.json`
的那一步抛了:

```
Error: UNKNOWN: unknown error, copyfile
  'packages/api-contract/openapi.json.guardbak' -> 'packages/api-contract/openapi.json'
  errno: -4094, syscall: 'copyfile'
```

后果三条,**一条比一条糟**:

1. `openapi.json` 被留在**篡改状态**(删了一个端点的那一版)
2. `openapi.json.guardbak` 留在工作区
3. **脚本崩在 `finally` 内部,没有任何一句话说明仓库已经被改坏了**

第三条是关键。如果那次没人去看工作区,下一次提交就会把一个残缺的对外契约推上去 ——
而**契约冻结检查会拿它当新基线**,于是被删掉的那个端点从此不再是「破坏性变更」。
一个守卫的失败,悄悄拆掉了另一个守卫。

## 原则

> **守卫要比较,就在内存里比。**
>
> 「备份 → 篡改 → 还原」是个坏形状:**还原那一步永远可能失败,而失败时仓库就坏了。**
> 用 `try/finally` 也救不了 —— 事故就发生在 `finally` 里面。

分三档,判据是**失败时留下什么**:

| 档    | 脚本                          | 允许写仓库?                        | 失败时的残骸                          |
| ----- | ----------------------------- | ---------------------------------- | ------------------------------------- |
| **1** | `check:*`                     | 🚫 **一律不允许**                  | ——                                    |
| **2** | `verify:*` 篡改**已跟踪文件** | ⚠️ 必须走 `scripts/lib/mutate.mjs` | 内容错误的**已跟踪文件** —— 最危险    |
| **3** | `verify:*` 创建**一次性夹具** | ✅ 允许                            | 未跟踪的目录 —— `git status` 一眼看见 |

### 第 1 档:`check:*` 必须是纯读

审计结果(2026-08-16):`check-contract` / `check-guards` / `check-oss-purity` /
`check-version` / `lib/scan` **全部只读**,一处写都没有。

这不是巧合,是它们的性质决定的 —— **检查的定义就是「看一眼,给个结论」**。
一个需要改动仓库才能得出结论的检查,基本可以断定是把「验证」与「被验证的东西」
搞混了。这一档由守卫钉住,不靠自觉。

`measure-process-cost` 也在这一档:它只往 `GITHUB_STEP_SUMMARY` 写(仓库之外)。

### 第 2 档:必须走受控通路

`verify-assertions` 的存在意义就是**弄坏真的产品代码**,确认测试真的变红。
这件事没法在内存里做 —— Vitest 解析的是磁盘上的真实路径,
而复制整个仓库(含 `node_modules`)每条探针一次是不现实的。

所以这一档不是「禁止写」,而是**「只能从一个地方写」**:
[`scripts/lib/mutate.mjs`](../../scripts/lib/mutate.mjs)。它把事故的三条后果逐条堵上:

| 事故                                     | 修法                                               |
| ---------------------------------------- | -------------------------------------------------- |
| 备份落盘,还原时可能读不回来              | **原文留在内存**,不产生 `.guardbak`                |
| `copyFileSync` 在 Windows 上抛 `UNKNOWN` | 还原改 `writeFileSync` + **退避重试 5 次**         |
| 崩在 `finally` 里,静默留下坏仓库         | 还原真失败时**打印可直接执行的恢复命令**并非零退出 |

⚠️ **注意第三条修的不是「不会失败」,是「失败时会被听见」。** 前两条降低概率,
第三条改变失败的**性质** —— 从「悄悄坏掉」变成「响亮地坏掉」。
这类问题上后者才是真正的收益:概率降不到零,可见性可以。

### 第 3 档:一次性夹具可以创建

`verify-guards` 会造 `packages/__guard_fixture__/` 这样的目录,让守卫真的扫到违规。
这个**不能**搬到仓库外 —— 守卫按设计遍历的就是仓库树,外面的文件它看不见。

允许它,是因为**失败形态不同**:清理失败留下的是一个**未跟踪的目录**,
`git status` 一眼看见,删掉即可;而第 2 档失败留下的是一个**内容错误的已跟踪文件**,
它会混进 diff、通过评审、成为下一次的基线。

约束两条:名字带 `__guard_fixture__` 前缀(一眼认得出是谁留下的),
且在 `finally` 里清理。
