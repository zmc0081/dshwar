# 测试宿主与运行宿主不同 —— 两边都对,而它们从未在同一个宿主里相遇

日期:2026-08-23(V0.9.0 Session 2)· 状态:已修 + 已机制化

> **形状**:测试是对的,代码是对的,而**产品从来没工作过**。
>
> 不是「测试写漏了一个分支」——那种情况下补一条断言就行。
> 这一族是:被测的那段代码在**测试宿主**里语义 A、在**运行宿主**里语义 B,
> 而断言只在 A 下成立。**覆盖率、断言强度、变异验证都发现不了它** ——
> 它们全都在同一个宿主里跑。

---

## 一、实例:SDK 在浏览器里从来没能工作过

`sdk/typescript/src/client.ts` 的构造函数,V0.5.0 起一直是:

```ts
this.fetchImpl = options.fetch ?? globalThis.fetch
```

`globalThis.fetch` 在浏览器里是 **`Window` 上的方法**。存进实例字段之后再
`this.fetchImpl(...)` 调,`this` 就成了这个 client —— 浏览器抛

```
TypeError: Failed to execute 'fetch' on 'Window': Illegal invocation
```

而 SDK 把它包成:

```
DshwarTransportError: request failed before a response was received
```

**这句话与「网络断了」「网关没起来」「DNS 解析失败」完全无法区分。**
V0.9.0 Session 2 接工作台时,查了好几步才落到这里:先怀疑 CORS(排除)、
再怀疑 effect 没跑(打探针,证明跑了两次)、再怀疑请求没发出
(网络面板确实没有,但那是**面板的局限**),最后在页内构造一个
「挑 `this` 的 fetch 替身」才复现出来。

### ⚠️ 为什么所有测试都是绿的

**Node 的 `fetch` 不在乎 `this`。** 它是一个普通函数,不是宿主对象上的方法。
于是:

|                                      | 测试宿主(Node / Vitest) | 运行宿主(浏览器)        |
| ------------------------------------ | ----------------------- | ----------------------- |
| `const f = globalThis.fetch; f(url)` | ✅ 正常                 | 🚨 `Illegal invocation` |

SDK 的每一条测试、契约测试、网关的 e2e —— 全都在 Node 里。
**它们证明的是「这段代码在 Node 里对」,而那从来不是要证明的事。**

## 二、它与「消费 dist 而非 src」是同族,但深一层

|                | V0.6.5 那次                       | 本次                                                 |
| -------------- | --------------------------------- | ---------------------------------------------------- |
| 形状           | 测试读的是**旧产物**              | 测试跑在**另一个宿主**里                             |
| 差异来自       | 时间(构建没跟上)                  | 空间(宿主语义不同)                                   |
| 修法           | 变异后同步 dist(`lib/mutate.mjs`) | **在测试宿主里复现另一个宿主的语义**                 |
| 能靠重建解决吗 | ✅ 能                             | ❌ **不能** —— 再怎么重建,Node 也不会开始在乎 `this` |

第四行是关键。前一族的解法是「让两边一致」;这一族两边**本来就不一致**,
而且不可能一致 —— 那正是它存在的原因。
所以解法不是消除差异,是**把差异搬进测试里**。

---

## 三、修法:在测试宿主里造一个「有另一个宿主语义」的替身

`sdk/typescript/test/browser-fetch.test.ts`:

```ts
// 与浏览器 Window.fetch 同形的替身:this 不是 host 就抛
function pickyFetch(this: unknown): Promise<Response> {
  sawHost = this === host
  if (this !== host) throw new TypeError("Failed to execute 'fetch' on 'Window': Illegal invocation")
  return Promise.resolve(new Response(…))
}
```

⚠️ **不能直接用 `globalThis.fetch`** —— 在 Node 里它就是不报错,而那正是问题所在。
用它写出来的测试会通过,并且看起来验过了。

两条断言各守一半:

| 断言                                | 守什么               | 少了它会怎样                       |
| ----------------------------------- | -------------------- | ---------------------------------- |
| 未绑定的 fetch → 客户端抛           | 复现了那个 bug       | 测试没测到任何东西                 |
| **绑定过的 fetch → 正常工作**       | 反向对照             | 一个「永远抛」的实现也能通过第一条 |
| 不传 fetch 时 `this === globalThis` | 默认路径真的 bind 了 | 只验了显式传 fetch 的那条路        |

**负向验证(已跑)**:把 `.bind(globalThis)` 去掉,第二条立刻红,
失败信息里带着 `Illegal invocation` 的因果链。

## 四、落到操作上:什么时候该问这个问题

> **「这段代码将来会在几个宿主里跑?测试跑在哪一个?」**

答案不是「一个」的时候,列出宿主之间**语义不同**的地方,逐条问
「测试宿主会不会把这处差异抹平」。

本仓已知的宿主差异:

| 差异                               | Node         | 浏览器                             | Tauri                             |
| ---------------------------------- | ------------ | ---------------------------------- | --------------------------------- |
| `globalThis.fetch` 的 `this`       | 不在乎       | **必须是 Window**                  | 同浏览器                          |
| 同源策略 / CORS                    | 没有         | 有                                 | 有,且前端源是 `tauri://localhost` |
| `EventSource` 能否带 Authorization | —            | **不能**(所以 SDK 用 fetch 读 SSE) | 同                                |
| `:focus-visible`                   | jsdom 不实现 | 实现                               | 实现                              |
| 文件协议下的 `popstate`            | —            | 触发                               | **不触发**(所以路由必须是 hash)   |

⚠️ 最后两行已经各自留下了记录(`design-system/test/focus-visible.html`、
`console-web/src/router.ts`),而第一行是这次才补上的。
**这张表本身就是「下次该问什么」的清单。**

## 五、这条约定的已知边界(明写)

它靠人执行。能自动查的只有一件事:**SDK 有没有那条浏览器语义的测试** ——
而「有没有覆盖到下一处宿主差异」查不到。

写在这里不是为了心安,是为了让下一个撞见同类问题的人知道:
**那不是 bug,是这条约定的已知边界** —— 以及,那时该做的是往上面那张表里加一行,
而不是只修当前这一处。
