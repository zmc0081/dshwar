# 没验证过的顺理成章

> **这一节是给半年后的人看的。**
>
> 它不记录某个决策,记录的是一类**反复出现的错误形状** ——
> 一个听起来顺理成章的因果解释,没人验证过,而它错了。
>
> 收录判据:必须是**已经写进文档、指导过决策、后来被实测推翻**的。
> 「当时想错了但很快发现」不收 —— 那是正常的思考过程,不是这里说的问题。

## 形状

```
观察到一个现象  →  想到一个解释  →  解释很顺  →  当成事实写进文档
                                        ↑
                              少了一步:去验证它
```

三个真实例子的共同点,一条比一条更值得记:

1. **解释得太好了。** 它把现象解释得严丝合缝,于是**没有留下"还需要看点什么"的感觉**。
   一个解释力弱的猜想会让人不安,不安会促使人去查;一个完美的猜想让人踏实,
   而踏实正是它危险的地方。
2. **因果链里有一个没被审视的箭头。** 写出来通常是两步,但只有第一步是已知的,
   第二步被默认了。
3. **没人写下"什么观察能推翻它"。** 而这恰恰是可验证与不可验证的分界。

## 例 1:「`runWithPrincipal` 是 AsyncLocalStorage,所以作用域过期了」

**现象**:agent 执行时读到的 principal 永远是 `ANONYMOUS`,文件全落进
`{root}/anonymous/anonymous/`。

**那个解释**:`runWithPrincipal(ctx, principal, fn)` 长得就像 ALS 的
`als.run(store, fn)`。而 ALS 有一个尽人皆知的坑:异步边界之外拿不到 store。
agent 是异步跑的 → 作用域早就出去了 → 读到匿名。

**为什么它特别顺**:它同时解释了症状、命中了一个真实存在的 JS 常见坑、
而且**不需要了解 cordis 的任何细节**就能说得通。

**实测三种形态,全否**:

| 形态                                 | 绑定可见? |
| ------------------------------------ | --------- |
| 在作用域外调 `create()`              | ✗         |
| **在作用域内的 ctx 上**调 `create()` | ✗         |
| **整轮都在作用域内**,await 到结束    | ✗         |

第三行是判决:**作用域全程活着,绑定依然看不见** —— 那就根本不是生命周期问题。

**真实机制**:`runWithPrincipal` 不是 ALS,是 `ctx.isolate(PRINCIPAL_BINDING)` +
`provide`,绑定只存在于**派生出来的那个 Context 对象**上。而 `agent.ctx` 派生自
`AgentRegistry` 插件自己的 fiber(插件加载时就定了,挂在根上),
与调用方传进去的那个 ctx 没有血缘关系。

**错的代价**:机制错 → 修法错。按 ALS 那套修,会去延长作用域、或改用
`enterWith` —— **两者都不会起作用**,而且会在一个恰好同步的测试里"看起来好了"。
更远一点:ALS 版本的故事暗示"这是个能修的 bug",而真相是**架构限制**
(四条路全部走不通),两者导出的产品决策完全相反 ——
一个是"下版修",一个是"逻辑档永远只支持单 principal,拒绝启动"。

📄 全部实测见 [`principal-scope-binding.md`](principal-scope-binding.md)。

## 例 2:「Linux 上 fork 更便宜,所以常驻内存更低」

**已知事实**:Linux 的 `fork()` 确实比 Windows 的进程创建便宜。这一半是对的。

**那个解释**:所以 Linux 上进程隔离的代价整体更低 —— 冷启动更快,内存也更省。
写进了 `FEASIBILITY-REPORT-V45.md` §6 与 README。

**实测(2026-08-16)**:

| 量       | Windows | Linux     | 差异    | 预期        |
| -------- | ------- | --------- | ------- | ----------- |
| 冷启动   | 115 ms  | **86 ms** | −25%    | ✅ 对       |
| 常驻 RSS | 58 MB   | **63 MB** | **+9%** | ❌ **反了** |

**没被审视的那个箭头**:「fork 便宜」→ _(默认了:所以所有内存相关的量都更好)_ →
「常驻更低」。而这两个量由**完全不同的机制**决定 —— 冷启动看进程创建与模块加载,
常驻看堆布局与运行时开销(glibc 的 malloc arena 与 Windows 堆管理器行为不同)。
**它们没有理由同向。**

**错的代价**:方向是**低估**,而低估落在容量规划上。50 人按 58 MB 算是 2.9 GB,
实际 3.2 GB —— 而部署方照着这个数买服务器。

📄 见 [`process-cost-thresholds.md`](process-cost-thresholds.md)。

## 例 3:「进程隔离能杀进程,所以顺带解决了没有 cancel 的问题」

收录它是因为它**错得最彻底:不只是错,方向是反的**。

**那个解释**:上游 stdio SDK 协议没有 cancel;进程隔离之后每个 principal 一个进程,
杀进程即是取消 —— 于是路线图把「解决 cancel」写成了 supervisor 的**收益**。

**实测**:**进程内**的 `Agent.cancel(cause)` 从 V0.2.0 起就可用,`AgentHandle.dispose()`
亦然,两者都真的截断输出。`DELETE /v1/sessions/{id}` 一直能用。
「没有 cancel」只适用于走 stdio SDK 协议的消费方 —— 而网关不走那条路。

反过来:进程隔离**把一个已经好用的取消变成了需要重新解决的问题**(子进程里的 agent
没有进程内句柄可调),最后靠三级降级才补回来。

**没被审视的箭头**:「协议里没有 cancel」→ _(默认了:所以我们没有 cancel)_ 。
前者说的是**某一条通路**,后者说的是**整个系统**。把一个局部事实提升成全局事实,
是这三个例子里最容易犯的一种。

📄 见 `ARCHITECTURE.md` §2.4 与 `docs/FEASIBILITY-REPORT-V45.md` §3。

## 怎么在下一次抓住它

**一条可执行的规矩,不是态度上的提醒:**

> 在把一个因果解释写进文档之前,**先写下什么观察能推翻它**。
> 写不出来,说明手上的不是一个理论,是一个故事。

对上面三个例子,这条规矩分别会问出:

| 例  | 该问的那句话                                   | 问了会怎样     |
| --- | ---------------------------------------------- | -------------- |
| 1   | 「如果作用域全程活着,绑定就该可见 —— 试过吗?」 | 十分钟就能证伪 |
| 2   | 「冷启动和常驻是同一个机制吗?」                | 立刻发现是两个 |
| 3   | 「哪条通路没有 cancel?网关走那条吗?」          | 立刻发现不走   |

### 两个补充的经验

**一、越是"不需要了解细节就能说通"的解释,越要验。** 例 1 的 ALS 故事只需要
JS 常识,例 2 只需要"Linux 更快"的常识。**不依赖具体知识的解释,通常也没被
具体知识约束过。**

**二、验证本身也会踩同一个坑。** V0.4.6 第一版探针**在根 ctx 上读 principal** ——
那里永远是匿名,**无论作用域有没有生效**。那条探针能"验证"任何结论。
写验证的时候要再问一遍:这个观察在假设为真和为假时,结果会不同吗?

### 与本仓其它机制的关系

这三条都是**文档层**的错误,而本仓对代码层的同类问题已经有机制:
`scripts/verify-assertions.mjs` 故意弄坏实现、确认测试真的变红,
治的正是"看起来在测、其实没测"。

**文档层还没有等价物,大概也不会有** —— 没法自动检验一句话有没有被验证过。
所以这份文档就是那个位置上唯一的东西:**靠读到它的人多问一句**。
