# 白牌品牌变量清单

日期:2026-08-18 · 状态:**四条前置事项已裁决;契约已接入,界面属 V0.7.0** · 关联:V0.7.0 开工前置项 #3

> **既定决策**:客户端白牌走**运行期主题**,品牌配置由服务端下发;
> **安装包永远中性**,一个二进制服务所有租户。
>
> 本文回答的是:**控制台与工作台界面上,哪些内容必须可被租户替换。**
> 它同时是两样东西 —— 设计需求的输入,以及配置契约的形状。
>
> **状态**:四条前置事项已由所有者裁决(见 §五),契约已接进
> `@dshwar/console-contract`。界面实现属 V0.7.0。

## 🚨 先读这一条:**应用图标不可白牌,这是决策的直接后果,不是遗漏**

> **写在最前面,因为第一个客户问起来时,它一定会被当成待办。**

| 能换                                             | 不能换                                                        |
| ------------------------------------------------ | ------------------------------------------------------------- |
| 界面内的一切品牌(logo / 主色 / 产品名 / favicon) | **操作系统层面的应用图标**:任务栏、程序坞、开始菜单、安装程序 |

**原因是既定决策的直接推论,不是能力缺失:**

> 「安装包永远中性,**一个二进制服务所有租户**。」

一个二进制,就只有一个应用图标 —— 它烧在安装包里,**运行期主题改不到那一层**。
要一租户一图标,就必须一租户一个安装包,而那与「一个二进制」直接矛盾。

**客户要自己的应用图标,唯一的路是白牌构建 + 客户自己签名**
(CI 模板已规划;签名主体就该是客户 —— 界面挂谁的品牌,签名就该是谁)。

⚠️ **这不是「以后支持」。** 除非推翻「一个二进制服务所有租户」,
否则它永远是这样。销售与售前应当按此口径回答,而不是记成一个待办。

## 零、三条前置裁决 —— 它们定下了契约的形状

写字段之前必须先答这三条,否则清单会写成一份看起来完整、实际落不了地的东西。
**三条均已由所有者裁决(2026-08-18)**,以下记录结论与理由。

### 裁决 1 · ✅ 认证前保持中性 —— 登录页不挂租户品牌

品牌配置是**租户级**的,而认证入口页(用户还没登录)时**服务端还不知道
他属于哪个租户**。于是「登录页挂客户品牌」不是一个字段问题,是一个架构问题。

**裁决:认证前保持中性。**

> ⚠️ **理由不是「这样简单」,而是:登录前服务端不知道你是谁,
> 任何品牌化都必然泄漏点什么。**

三个方案各自泄漏什么,写清楚才看得出这不是取舍而是排除法:

| 方案                                   | 泄漏什么                                                                                                                 |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| A. 按 hostname 提供公开的品牌端点      | **把租户列表变成可枚举资源。** 对 ToB 产品,**客户名单本身就是敏感信息** —— 竞争对手拿它做销售线索,监管方拿它推断业务范围 |
| C. 客户端本地缓存上次的品牌,登录前先用 | **把 A 公司的存在泄漏给共用设备上 B 公司的员工。** 咨询公司的共享笔记本、外包商的工位机,这不是边缘场景                   |
| **B. 认证前中性(选中)**                | 不泄漏。代价只是白牌感在第一屏缺席                                                                                       |

⇒ A 与 C 泄漏的**都不是我们的信息,是客户的客户名单**。
那不是我们有资格拿去换观感的东西。

#### 预留:租户专属登录 URL(V0.7.x 增强,本次不实现)

有一条不泄漏的路:让租户拿到一个**专属登录入口**,访问它即可直接套主题 ——
因为访问者已经通过 URL 本身声明了自己属于哪个租户。

⚠️ **句柄必须是随机不可猜的,不能是公司名。**
`/s/acme` 与 `/s/globex` 一样可枚举 —— 它把「猜 hostname」换成了「猜路径」,
一点也没变好。必须是 `/s/k7m2x9pq4w` 这类无语义的随机串。

契约里**预留字段但不实现**(见 §四 的 `signInHandle`),理由:
预留一个字段的成本是一行,而**事后加一个会改变 URL 空间的字段**要动
路由、部署文档、客户已经发出去的链接。

| 属性     | 决定                                                               |
| -------- | ------------------------------------------------------------------ |
| 生成方   | **服务端**,租户不可自选(自选就会有人选 `acme`)                     |
| 可轮换   | 是 —— 泄漏了要能换,而换掉旧链接即失效                              |
| 排期     | **V0.7.x**,V0.7.0 不做                                             |
| 不做之前 | `signInHeadline` / `signInSubtext` 在首屏不生效,只在已知租户时有用 |

### 裁决 2 · ✅ 资产自托管,不接受外部 URL

四条理由,任一条都足够。**第一条是企业安全评审会直接问的那一条**:

1. ★ **外链等于向那台服务器报告客户每个员工的每次访问。**
   每次页面加载,每个员工的浏览器都会向持有资产的服务器发一次请求 ——
   IP、User-Agent、时间、频次全都过去。而在托管白牌形态下,**那台服务器就是我方**。
   **企业安全评审的第一个问题就是「你们的产品会不会让我们员工的浏览器往外发请求」**,
   而「会,每次都发,发给供应商」是一个能直接卡住采购的答案。
   自托管之后,请求落在客户**已经信任并部署了的**那套系统上,评审无从问起。
2. **离线**(V0.6.5 的核心卖点):外链 logo 在内网/断网部署里是一个碎图标。
   「数据不出内网」的客户不会接受界面去公网拉图。
3. **CSP**:Tauri 与本地 sidecar 下的内容安全策略要显式放行来源,
   而「租户可填任意 URL」与「CSP 白名单」天然冲突。
4. **完整性**:外链资产可被持有方随时替换,而界面上那个位置是客户的品牌。

⇒ 字段类型是**控制平面内的资产引用**(上传后拿到的 id 或路径),不是 `https://…`。

### 裁决 3 · ✅ 发票卖方是**显式字段**,默认留空,**未配置时拒绝出票**

初稿把这条写成了「客户 or DSHWAR」的二选一。**那个提法本身是错的** ——
它把一个法律与商业模式问题压缩成了一个 boolean,而两个答案指向的是
**两种不同的生意**,不是同一门生意的两个开关位置。

**裁决:不做 boolean,做显式字段。默认留空;未配置时拒绝出票。**

| 判据                     | 内容                                                                                                                   |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| **为什么不做默认值**     | 发票是**法律文件**。给它一个默认卖方,等于替客户签了字。宁可拒绝出票 —— 拒绝发生在配置时,错误的发票发生在客户的客户那里 |
| **自建者天然有答案**     | `billing-stripe` 开源(D4)之后,自建者用**自己的 Stripe 账号**收款 —— 钱进他的账户,卖方天然就是他。这一档没有选择余地    |
| **只有托管服务才有选择** | 托管形态下钱先进谁的账户是商业模式问题,**技术上两种都支持**                                                            |
| **商业决定**             | 由所有者另行确定,**不阻塞技术实现**                                                                                    |

⇒ `legalEntityName` **保持「界面显示用,不进发票」**。发票卖方是**另一个字段、
另一个契约**(`@dshwar/billing`),两者刻意不复用 ——
一个填错只是页脚难看,另一个填错是开错发票。

#### 落地范围 —— ✅ **已实现**(2026-08-18)

| 要动的地方                | 实际改成                                                                  |
| ------------------------- | ------------------------------------------------------------------------- |
| `Invoice`                 | 增 `seller: InvoiceSeller`,**非可选**                                     |
| `LocalBillingOptions`     | 增 `seller`,**必填** —— 见下方「提前到装配期」的评估                      |
| `LocalBilling` 构造函数   | 断言卖方已配置 → **拒绝启动**                                             |
| `Billing.generateInvoice` | 契约写明:卖方未配置**必须抛** `SellerNotConfiguredError`,不得返回占位发票 |
| 负向验证                  | 单测 13 条 + **常驻探针 15**(把拒绝改成静默降级 → 断言变红)               |

##### 「未配置」与「显式配置为空」在**类型层**就分开

- **未配置** = `seller` 缺席(`undefined`)
- **显式为空** = `legalName` 是空串 —— 而它**根本赋不进来**:
  `LegalEntityName` 是品牌类型,裸 `string` 赋值不了,必须过 `legalEntity()`,
  而 `legalEntity('')` 的参数类型是 `never`,**写出来就编译不过**

⚠️ **两层各管一段,不要冒充彼此**(实测确认):

| 层     | 管什么                       | 拦不住什么                                   |
| ------ | ---------------------------- | -------------------------------------------- |
| 类型层 | 代码里**写死**了空串字面量   | 动态 `string`(`string extends ''` 为假,放行) |
| 运行时 | **配置文件**里填了空串或空白 | —                                            |

两者抛的错**刻意不同**:`EmptyLegalEntityError`(有人以为空白合法)
与 `SellerNotConfiguredError`(这一项还没填)—— 原因不同,不合成一个。

##### ✅ 评估结论:自建档的卖方**提前到装配期**必填

**成立,已按 fail-closed 惯例实现。** 三条依据:

1. **这一档的卖方没有选择余地** —— `billing-stripe` 开源后自建者用自己的
   Stripe 账号,钱进他的账户。「未配置」在这里**不是待定的商业选择,
   是纯粹的配置遗漏**,与逻辑档 + 多用户那条启动闸门同级
2. **判据是「装了这个插件的人意图是什么」** —— `LocalBilling` 的方法全是发票;
   只想看用量不出账的人根本不装它(走 `summarizeLocalUsage` 就够)。
   ⇒ **装了它 = 打算出票 = 卖方是必需配置**
3. **时机差别很实际** —— 不拦在装配期,配置遗漏要到**第一次出票**才显形,
   而第一次出票通常是**月底**:出账窗口有限,能改配置的人可能正好不在

⚠️ **出票时仍然再断言一次**,两条理由:契约要求**所有**实现方都拒绝出票
(对 `billing-hosted` 同样成立),以及类型可以被 `as` 掉而断言不会。

##### 契约冻结不受影响(已实测)

`Invoice` 加必填字段是 `@dshwar/billing` 的破坏性变更,但**发票不经 `/v1` 暴露**
(只有 webhook 端点在)—— 契约冻结检查实测 **破坏性 0 处**。窗口在关上之前赶上了。

## 一、正面清单:必须可被租户替换

| 字段名              | 类型                | 必填 | 默认值                     | 影响的界面位置                                                                     |
| ------------------- | ------------------- | ---- | -------------------------- | ---------------------------------------------------------------------------------- |
| `productName`       | `string`(≤ 40 字符) | ✅   | `"DSHWAR"`                 | 浏览器标题 · 顶栏 wordmark · 关于页 · 空状态文案 · 认证入口页(见裁决 1)            |
| `logoLight`         | `AssetRef \| null`  | ❌   | `null` → 回落文字 wordmark | 顶栏(浅色主题)· 关于页 · 登录页(见裁决 1)                                          |
| `logoDark`          | `AssetRef \| null`  | ❌   | `null` → 回落 `logoLight`  | 同上(深色主题)                                                                     |
| `favicon`           | `AssetRef \| null`  | ❌   | `null` → 回落项目默认      | 浏览器标签页 · 书签 · PWA 图标 · Tauri 任务栏(见下注)                              |
| `primaryColor`      | `HexColor \| null`  | ❌   | `null` → 中性外观(无彩)    | 主按钮 · 链接 · 选中态 · 焦点环 · 图表主色 · 进度条                                |
| `accentColor`       | `HexColor \| null`  | ❌   | `null` → 由主色派生        | 次级强调 · 徽标 · 标签                                                             |
| `supportUrl`        | `HttpsUrl \| null`  | ❌   | `null` → 隐藏入口          | 顶栏「获取帮助」· 错误页脚 · 容量页超限提示的下一步                                |
| `supportEmail`      | `Email \| null`     | ❌   | `null` → 隐藏              | 同上(与 `supportUrl` 至少给一个,否则求助无门)                                      |
| `docsUrl`           | `HttpsUrl \| null`  | ❌   | `null` → 隐藏              | 帮助菜单 · 首次使用引导                                                            |
| `legalEntityName`   | `string \| null`    | ❌   | `null` → 隐藏版权行        | 页脚版权行(⚠️ 见裁决 3 —— **不**进发票)                                            |
| `privacyPolicyUrl`  | `HttpsUrl \| null`  | ❌   | `null` → 隐藏              | 页脚 · 首次登录的同意环节(若有)                                                    |
| `termsOfServiceUrl` | `HttpsUrl \| null`  | ❌   | `null` → 隐藏              | 同上                                                                               |
| `signInHeadline`    | `string`(≤ 60)      | ❌   | 由 `productName` 生成      | 认证入口页主标题 —— **V0.7.x 之前首屏不生效**(裁决 1)                              |
| `signInSubtext`     | `string`(≤ 160)     | ❌   | `null` → 隐藏              | 认证入口页副文案,同上                                                              |
| `signInHandle`      | `string \| null`    | —    | `null`(恒定)               | 【**预留,V0.7.x**】租户专属登录入口的随机句柄。**租户不可自选**,服务端生成、可轮换 |

`AssetRef` = 控制平面内的资产引用(见裁决 2),**不是任意 URL**。

⚠️ **发票卖方不在本表内**(裁决 3)—— 它属于 `@dshwar/billing`,
与 `legalEntityName` 刻意不复用。

### 逐项说明(只写不显然的那些)

#### `productName` —— 两条约束,一条是法律的

**替换范围包括浏览器标题**,因为那是白牌感最先被戳破的地方:界面挂着客户
logo,标签页写着 DSHWAR。

⚠️ **两条约束**:

1. **不得含 "DeepSeek"**(CLAUDE.md §9:项目名不含 DeepSeek,对上游的引用
   限于指名性使用)。这条**必须在配置写入时校验并拒绝**,而不是在渲染时过滤 ——
   拒绝发生在管理员面前,过滤发生在用户面前,前者能改后者不能。
2. **DSHWAR 无法替客户做商标尽调。** 客户填什么名字是客户的法律责任,
   配置页面上应当有一句话说明这一点。这不是免责话术,是**把责任放在能承担
   它的一方** —— 我们既不知道客户在哪些法域经营,也不知道他注册了什么。

#### `logoLight` / `logoDark` —— 为什么是两个字段而不是一个自动反色

自动反色对**单色标志**有效,对**带渐变或摄影元素的标志**会毁掉它。而
「我们的 logo 在深色背景上要用另一版」是品牌方的常识,不是边缘情况。

**回落链是刻意的三级**:`logoDark` 缺 → 用 `logoLight`;`logoLight` 也缺 →
**用 `productName` 的文字 wordmark**,而不是显示 DSHWAR 的 logo。
最后一级是关键:**一个只填了产品名、没传 logo 的租户,界面上不该出现我们的标志。**

#### `favicon` —— 为什么与 logo 分开

宽高比与尺寸完全不同(logo 常是横向 wordmark,favicon 是 16–512 的正方)。
自动裁切横向 logo 得到的 favicon 通常只剩一个字母的一部分。

⚠️ **Tauri 的任务栏/程序坞图标不在此列** —— 那个图标烧在**安装包**里,
而既定决策是「安装包永远中性」。运行期主题改不了它,**这是决策的直接后果,
不是遗漏**:一个二进制服务所有租户,就不可能每个租户一个应用图标。
客户要自己的应用图标,必须走**客户自己签名的白牌构建**(CI 模板已规划)。

#### `primaryColor` —— 只收种子色,**色阶由客户端派生**

**不开放整条色阶让租户逐档填**,理由有二:

1. **十档手挑必然不一致** —— 而不一致的色阶会让界面看起来是坏的,
   而不是「客户品牌的」。
2. **对比度无法保证**:租户挑一个浅黄做主色,白底上的主按钮文字就读不了。
   派生算法可以**保证每一档与其配对前景色的对比度达标**(WCAG AA ≥ 4.5:1),
   逐档手填做不到。

⚠️ **写入时校验,不在渲染时兜底。** 校验的是**派生结果**的三项下限,
不是种子色本身 —— 种子色好不好看不是判据,派生出来的角色令牌能不能读才是:

| 令牌                    | 对比度下限 |
| ----------------------- | ---------- |
| `accent.text`           | ≥ 4.5      |
| `accent.border`         | ≥ 3.0      |
| `accent.surface` 上墨字 | ≥ 7.0      |

不达标**拒绝保存并说明原因**,而不是悄悄换一个近似色。
悄悄换的后果是客户以为自己设了品牌色,看到的却不是它 —— 而他会认为是 bug。

> 这与本仓「安全默认优先 —— 认不出或不安全就拒,不降级服务」是同一条判据,
> 只是这次「不安全」指的是**读不了**。

⚠️ **实心填充落在中亮带 `L ∈ (0.55, 0.80)` 被重打光时,保存前必须回显
原色与重打光结果并要求管理员确认。这是阻塞步骤,不是提示** ——
一个可以划过去的提示等于没有:管理员会在「我设的颜色没生效」的工单里
才第一次注意到它。

#### ⚠️ V0.8.0 回写:`string` → `string | null`,默认值移除

设计侧核对时发现**两处**(详见 [`design-system-sync.md`](design-system-sync.md)):

1. **旧默认色 `#2F6FEB` 的 L = 0.573,落在中亮带内** ——
   契约一边要求「带内要阻塞确认」,一边把一个带内的值设成默认,
   于是那条确认流程**在默认路径上永远走不到**,等于半条死代码。
2. **用默认值冒充「未配置」** —— 与 V0.6.0 的发票卖方字段同形:
   两种状态必须在**类型层**可分,靠哨兵值区分是运行时约定,
   而运行时约定会被下一个人当成普通值。

⇒ `primaryColor` 改为 `string | null`(`null` = 未配置 = 中性无彩),
默认值移除;另出一个**建议起点**常量 `SUGGESTED_PRIMARY_COLOR = '#1D5BD4'`
(L 0.509,带外,策略 VERBATIM)。

**建议 ≠ 默认**:默认值会让「未配置」不可见,而建议值只在管理员**主动采纳**
时才成为配置 —— 采纳这个动作本身就把状态从「未配置」变成了「配置成这个值」。

⚠️ **禁止 `?? '#2F6FEB'` 之类的兜底**:那会把类型层刚区分开的两种状态在
第一个调用点重新合并 —— 类型上仍分开,行为上又合并,**且不会有任何东西变红**。
判空**收敛在派生入口一处**(`derive(seed: string | null)`),不在调用点判。
由 `check-guards.mjs` 的「primaryColor 的 null 不许被兜底掉」守着,
负向验证 30a/30b + **正向对照 30c**。

#### `signInHeadline` / `signInSubtext` —— 范围比名字看起来小得多

⚠️ **DSHWAR 不实现登录**(硬规则 4:不存密码、不签发身份令牌、不做注册流程)。
所谓「登录页」是一个**认证入口页**:它的全部职责是把用户送去客户自己的 IdP。

所以这里能替换的只有**引导文案**。以下**不属于**本字段范围,因为它们根本
不在我们的页面上:

- IdP 自己的登录表单、密码规则提示、MFA 引导 —— 那是 Keycloak / Entra 的界面
- 「忘记密码」「注册账号」 —— 我们没有这些流程,也不该有入口

⇒ **裁决 1 定的是认证前中性**,所以这两个字段**在首屏不生效** ——
它们只在「已经知道是哪个租户」的场景下有用(切换租户、以及 V0.7.x 的
租户专属登录入口 `signInHandle`)。

**仍然保留在契约里**,因为 `signInHandle` 一旦落地它们就立刻有用武之地,
而那时再加字段要动的是已经发布的契约。**留一个字段比事后加一个便宜。**

### 🚨 为什么隔离档警告绝对不能开放

这是整份清单里最值得写清楚的一条。当前文案(真实代码):

> 「逻辑隔离档,只支持一位成员。要加人请把 `isolation.level` 改成 `"process"`
> (每位成员约 63 MB)。」

它守的不是「体验」,是一个**会静默发生的数据事故**:逻辑档下多 principal
**根本没有分隔** —— 所有人的文件都落进 `anonymous/anonymous/`,**互相覆盖
且没有任何报错**(见 `principal-scope-binding.md`)。

**想改这句话的人,是嫌它挡路的人。** 而嫌它挡路,恰恰因为他正要做那件
它拦着的事。**一个能被劝阻对象自己关掉的警告不是警告。**

⚠️ 同理,容量数字(`memberCap` / `rssPerProcessMb` / `basis`)也不开放 ——
它们由服务端 `deriveMaxProcesses` 算出,是**管理员据以买服务器**的依据。
可改 = 可以把「上限 39」改成「上限 200」,而机器不会因为界面上的数字变大而变大。

## 三、横切约束(不是字段,但同样是契约的一部分)

| 约束                                    | 理由                                                                                            |
| --------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 品牌配置**经统一 SDK 层**获取           | D7 约束 3。三个宿主(远端 Web / 本地 sidecar / Tauri)只差 `baseURL`,散落的 fetch 在 Tauri 下全挂 |
| 资产由控制平面托管,**不接受外部 URL**   | 裁决 2 —— 外发请求、离线、CSP、完整性 四条                                                      |
| 主题在**运行期**套用,不进构建产物       | 既定决策。一个二进制服务所有租户                                                                |
| 品牌配置变更**进审计**                  | 改产品名与法律实体是对外可见的动作,与改配额同级                                                 |
| 未配置任何品牌时 = **中性 DSHWAR 外观** | 开源自建模式的默认。不是「半成品状态」,是一个完整的、受支持的形态                               |
| 品牌字段**不参与任何权限判定**          | 显示层就是显示层。一旦有代码按 `productName` 分支,白牌就从换肤变成了分叉                        |

## 四、契约(已接进 `@dshwar/console-contract`)

> 下面是**实际落地的形状**,不再是草案。权威源是
> `packages/console-contract/src/branding.ts`,本节与它同步。

```ts
/** 控制平面内的资产引用。**不是 URL** —— 见 §零 裁决 2。 */
export interface AssetRef {
  readonly id: string
  /** 供 <img> 使用的、由控制平面提供的相对路径。前端不拼这个字符串。 */
  readonly path: string
}

/**
 * 租户品牌。**全部字段都只影响显示层** —— 没有任何一个参与权限判定。
 *
 * ⚠️ 不在此结构里的东西同样是决策:隔离档警告、降级提示、错误码、
 * 审计词表、上游归属声明**刻意不可替换**,理由见 branding-variables.md §二。
 */
export interface TenantBranding {
  readonly productName: string
  readonly logoLight: AssetRef | null
  readonly logoDark: AssetRef | null
  readonly favicon: AssetRef | null
  /** `#RRGGBB`。写入时校验对比度,不达标**拒绝保存**。 */
  /** `null` = 未配置 → 中性外观(无彩)。**不要给它默认值。** */
  readonly primaryColor: string | null
  readonly accentColor: string | null
  readonly supportUrl: string | null
  readonly supportEmail: string | null
  readonly docsUrl: string | null
  readonly legalEntityName: string | null
  readonly privacyPolicyUrl: string | null
  readonly termsOfServiceUrl: string | null
  readonly signInHeadline: string | null
  readonly signInSubtext: string | null
  /** 预留:租户专属登录入口的随机句柄。V0.7.x 之前恒为 null。 */
  readonly signInHandle: string | null
}
```

⚠️ **建议起点是独立常量,不是默认值**:

```ts
export const SUGGESTED_PRIMARY_COLOR = '#1D5BD4' // L 0.509,带外 → VERBATIM
```

⚠️ **色阶不在契约里** —— 客户端由 `primaryColor` 确定性派生。
放进契约就等于允许两端各派生一套,而那两套迟早会不一样。

⚠️ **发票卖方不在这个结构里**(裁决 3)—— 它属于 `@dshwar/billing`。
两者刻意不复用:`legalEntityName` 填错只是页脚难看,卖方填错是开错发票。

### 字体为什么不开放 —— 法律风险是第一位的,体积是次要的

1. ★ **多数商用字体禁止再分发,而分发的是我们的产品。**
   客户上传一个他自己买了授权的字体,我们把它作为产品的一部分分发给
   **他的每一个终端用户** —— 那份授权通常不覆盖这种用法。
   **违约方看起来是客户,而实际执行分发的是我们**,追究起来两边都在里面。
   要开放就得先答:**谁去核验每个租户上传的字体有没有再分发授权?**
   这个问题没有便宜的答案 —— 而没有答案就不该开这个口子。
2. 体积:自托管字体文件动辄数 MB × 多字重 × 多字集(中文尤甚),
   而它对白牌感的贡献远小于 logo 与主色。**这条只是次要理由,不是主要理由。**

⚠️ 记在这里是为了**免得下次有人当遗漏补上去** —— 「字体没列」是决策,不是疏忽。
