# 同一个字段上的两个洞:分两次动会挑错形状

> **形状**:一个字段上挂着两个**互相牵制**的缺陷,而每一个单独看都有一个
> 看起来足够的修法 —— 那两个修法**互不兼容**。先动的那一个会把形状定死,
> 第二次来的人只能在一个装不下的形状里将就。

V0.9.0 Session 5.5 实测。记在这里不是为了记住 `costMinorUnits`,
而是为了下一次遇到「这个字段还有另一个问题,回头再说」时能认出来。

---

## 那两个洞

`UsageRecord.costMinorUnits: integer` + `currency: string`,V0.6.0 起挂着。

| #   | 洞           | 症状                                                                     | 谁受害                                  |
| --- | ------------ | ------------------------------------------------------------------------ | --------------------------------------- |
| 一  | **语义折叠** | 「模型没配价(**算不出来**)」与「部署方不计费(**不收钱**)」产出同一个 `0` | 拿账单对账的人:两者的处理**完全相反**   |
| 二  | **单位假设** | 契约注释写死「分」,消费方一律 `÷ 100`;而 ISO 4217 的指数不都是 2         | JPY 差 **100 倍**,KWD 差 10 倍,方向相反 |

两个洞的发现相隔两个版本(洞一在 V0.6.0 的哨兵审计里,洞二在 V0.9.0 Session 3
写用量页时)。中间那段时间里,洞一有一个写好的、看起来足够的修法。

---

## 🚨 关键:那个「足够的修法」装不下第二个洞

洞一的直觉修法是给「算不出来」一个独立表达 —— `number | null`,或者
在旁边加一个 `costBasis: 'priced' | 'unpriced' | 'not-billable'`。

洞二的修法是给金额**带上单位**(币种 + 指数)。

⇒ 一个 `number | null` 要装的是**四件事**:

> 多少钱 · 什么币种 · **几位小数** · **算不算得出来**

它只能装两件。先按洞一改成可空数字,再来修洞二时会发现:
指数没地方放,于是只能在旁边再加一个字段,而那时
`amountMinor: null` 与 `currencyExponent: 2` 并存 —— 一个「没有金额却有小数位」
的对象。形状已经被第一次改动定死了。

**而两次改动都是契约的破坏性变更。** 分两次 = 破坏性变更做两遍,
第二遍还得在一个自己挑错了的形状上做。

---

## 判据:什么时候必须一起动

> **两个缺陷是不是要改**同一个字段的形状**?**

是 → 一起动,并且**先把两条一起摆出来再决定形状**。
不是(比如一个改行为、一个改文案)→ 分开动没有代价。

⚠️ 判据**不是**「两个缺陷有没有关系」。它们的关系可以很远
(一个是语义、一个是单位),关键只在**改动落在哪里**。

---

## 落地形状,以及三处与「建议修法」的差别

最终是一个判别联合(`packages/metering/src/cost.ts`):

```ts
type Cost =
  | { kind: 'priced'; amountMinor: number; currency: string; currencyExponent: number }
  | { kind: 'unpriced' } // 算不出来
  | { kind: 'unbilled' } // 不收费
```

| 审计时的建议                                | 实际做法                    | 为什么改                                                                                      |
| ------------------------------------------- | --------------------------- | --------------------------------------------------------------------------------------------- |
| 在旧字段旁加 `costBasis`                    | **换掉整个字段**            | 并行字段允许 `costBasis: 'unpriced'` 与 `costMinorUnits: 0` 并存 —— 歧义还在,只是多了一个字段 |
| `not-billable` 由本地 provider 列表**推断** | `unbilled` 由部署方**声明** | 推断需要把列表喂进定价函数,而「哪些算本地」本身又是一张会分家的清单                           |

## ⚠️ 顺带的一条:指数不要放进任何一张表

洞二有一个很自然的错误修法:**在消费方放一张「币种 → 指数」表**。

改动前的 `console-web` 里**已经有两处**各自解决了这个问题,而它们的答案不一样:

| 位置               | 做法           | JPY 的答案    |
| ------------------ | -------------- | ------------- |
| `view/overview.ts` | 自带 11 条的表 | 对            |
| `view/usage.ts`    | 写死 `÷ 100`   | **差 100 倍** |

一个前端里的两个事实源,而没有任何东西会红。

⇒ 指数**随金额一起从契约来**,而服务端的指数与它的价格出自**同一段配置**
(`governance.pricing`)—— 两者由同一个人在同一次编辑里写下,不存在分家的路径。

🚨 **服务端也不许有这张表**:那会是一份会过期的数据(币种改制真的发生过),
一过期,正确的配置反而会被判成错的。

**谁验证它**:`check-guards.mjs` 的「没有人自带币种指数表」守卫,
反向对照 `verify-guards.mjs` 42b/42c(`currency: 'JPY'` 与 `currencyExponent: 2`
都是合法写法,不能被误伤)。
