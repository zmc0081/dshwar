# `/v1` 如何携带 `workspaceId`

> V0.4.1 Session 1 · R6 · 2026-08-16
> **结论:选项 A 的变体 —— 建会话时传,之后由会话 id 承载。**
> **兼容性:相容变更(additive),不升大版本,不触发双版本并行义务。**

---

## 约束

`/v1` 契约在 V0.2.0 Session 6 冻结。任何变更由 `pnpm check:contract` 比对
上一次提交的 OpenAPI 并分类:相容的放行,破坏性的必须有一份点名
`@dshwar/api-contract` 的 `major` changeset。

`ARCHITECTURE.md` 风险登记第 11 条把这件事列为风险:
「`/v1` 契约因 `workspaceId` 而变更 → 破坏下游」,应对是
「V0.4.1 Session 1 先出决策文档并显式声明兼容性」。本文件即是那份声明。

---

## 三个候选

| 选项   | 形态                                  | 契约影响                                        |
| ------ | ------------------------------------- | ----------------------------------------------- |
| A      | 查询参数 `?workspaceId=`              | 加**可选**查询参数 → 相容                       |
| B      | 路径段 `/v1/workspaces/{id}/sessions` | 新增路径 → 相容;但若同时废弃旧路径 → **破坏性** |
| **A′** | **建会话时传,之后由会话 id 承载**     | **相容** ← 选它                                 |

### 为什么不是 B

B 读起来最"REST",但代价被低估了:

1. **旧路径怎么办?** 保留 → 两套路径长期并存,每加一个端点要加两遍;
   废弃 → 破坏性变更,升大版本 + v1 与新版本并行不少于 6 个月(本版本红线第 4 条)。
   V0.4.1 是个 **3 天**的版本,不该背这个。
2. **工作区不是会话的父资源。** 会话属于**主体**,工作区只是它干活的地方。
   把工作区做成路径前缀,等于声明「会话是工作区的子资源」——
   将来要支持一个会话跨工作区读文件(完全可能)时,这个层级就成了谎言。

### 为什么不是纯 A

查询参数放在**每一个**会话端点上,意味着调用方每次请求都要带,漏带一次就落到
`default`。而「漏带」是静默的 —— 用户会发现文件不见了,但不会知道为什么。

### A′:只在建会话时传一次

```
POST /v1/sessions
{ "workspaceId": "proj-a", ... }        ← 可选，省略即 default

→ Session { "id": "...", "workspaceId": "proj-a", ... }
```

此后 `POST /v1/sessions/{id}/turns`、SSE、DELETE **都不需要再带** ——
会话 id 已经承载了工作区。这消除了「漏带」这一整类错误。

列表端点加一个**可选**过滤参数:

```
GET /v1/sessions?workspaceId=proj-a     ← 省略即返回全部工作区的会话
```

省略时返回全部,与改造前行为一致 —— 这是 R2「向后兼容」在 API 层的延续。

## 兼容性声明

按 `packages/api-contract/src/freeze.ts` 的分类规则:

| 变更                                                | 分类 | 依据                             |
| --------------------------------------------------- | ---- | -------------------------------- |
| `CreateSessionRequest` 加**可选**字段 `workspaceId` | 相容 | `property.added`,未进 `required` |
| `Session` 加**可选**字段 `workspaceId`              | 相容 | 同上                             |
| `GET /v1/sessions` 加**可选**查询参数               | 相容 | 非 `parameter.required.added`    |

**三项全部相容。不升大版本,不触发 6 个月双版本并行义务。**

⚠️ 两条不能踩的线:

- `Session.workspaceId` **必须是可选的**。语义上每个会话都有工作区,
  但把它加进 `required` 会让老客户端的响应校验失败 —— 那是破坏性变更。
  可选但恒有值,是 API 兼容演进的标准做法,不是含糊其辞。
- **不得删除或改名任何现有字段**。`check:contract` 会拦,但更重要的是
  没有理由这么做。

风险 11 至此**降级为已处置**:契约变更是相容的,下游不受影响。

## 实现要点

1. `TenantFileSystem.workspaceOf` 由网关注入,读当前会话的 `workspaceId`。
2. 会话簿(`GatewaySessionStore`)记录 `workspaceId`,与 `subjectId` 同级 ——
   它是归属信息的一部分。
3. **跨工作区访问按 404 处理**,与跨主体一致:调用方无法区分「不存在」与
   「不属于你」。理由见 `gateway/src/errors.ts` 的 `notFound()`。

---

## 什么时候会推翻

出现「一个会话需要同时读写多个工作区」的需求时。那时 `workspaceId` 会从
会话的**属性**变成每次操作的**参数**,形态更接近纯 A。

那不是破坏性变更:给操作加可选参数仍是相容的,会话上的字段可以保留为默认值。
**这条退路是选 A′ 而不是 B 的另一个理由** —— B 的路径层级一旦定死就退不回来。
