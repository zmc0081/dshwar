# 决策:工作区的产品语义

> **状态**:✅ **已定案**(V0.5.0,2026-08-16)。此前一直挂起,
> 而挂起本身在阻塞另一个决策 —— 见文末「它同时关掉了什么」。

## 定案

> **每用户多工作区。工作区是项目容器,不跨用户共享。**

三句话各自有后果,拆开说:

| 定的是什么           | 直接后果                                                                                                  |
| -------------------- | --------------------------------------------------------------------------------------------------------- |
| **每用户多工作区**   | 路径模型 `{root}/{tenantId}/{userId}/{workspaceId}` 的四段全部有意义,没有一段是常量                       |
| **工作区是项目容器** | 它的粒度对齐「一个项目 / 一件事」,不是「一次会话」也不是「一个团队」                                      |
| **不跨用户共享**     | 协作不通过共享工作区实现。要协作,走导出 / 导入或将来的显式共享机制 —— 那是另一个特性,不是工作区的默认语义 |

## 为什么是这三条

### 「每用户多工作区」而不是「每用户一个」

一个人同时在做的事不止一件,而 agent 的工作区里堆的是**文件**:
把三个项目的文件混在一个目录里,agent 的 `ls` 和 `grep` 会互相干扰 ——
这不是洁癖问题,是**上下文污染会降低 agent 的实际表现**。

### 「项目容器」而不是「会话容器」

会话是短的、可丢弃的;项目是长的、要回来继续的。
若工作区对齐会话,每次新会话都得重新准备一遍文件 —— 那等于没有工作区。

### ★ 「不跨用户共享」是这里最有分量的一条

因为它**否定了一个看起来很自然的产品形态**:「团队共享工作区」。

否定的理由不是技术上做不到,是**它与隔离模型冲突**。DSHWAR 的隔离
沿 `{tenantId}/{userId}` 两段展开;工作区一旦跨用户,
`userId` 那一段就不再是边界,而**它同时是凭据解析、配额归属、审计 actor
的那一段**。共享工作区意味着这四样东西要各自重新定义边界 —— 那是四个决策,
不是一个特性。

要协作,该做的是**显式的共享机制**(谁把什么共享给谁、什么时限、什么权限),
而不是把默认语义放宽。**放宽是不可逆的**:一旦有用户依赖了共享工作区,
再收紧就是破坏性变更。

## 它同时关掉了什么

**「一租户一进程」方案,不做。**

那个方案(见 [`one-process-per-tenant.md`](one-process-per-tenant.md))
的做法是:进程内在根上 provide 一个 `userId` 为哨兵值的 principal,
于是整租户的 agent 都落到 `{root}/{tenant}/<哨兵>/default/`。
50 人从 50 进程降到 1 进程,内存省一到两个数量级。

**它与本决策直接冲突** —— 它把 `userId` 那一段**变成常量**,
而本决策说那一段有意义。这不是可以调和的两种配置:

|             | 本决策     | 一租户一进程       |
| ----------- | ---------- | ------------------ |
| `userId` 段 | 真实用户   | 常量哨兵           |
| 工作区归属  | 每人私有   | 整租户共享         |
| 计量归属    | 真实发起人 | 哨兵(整租户一个数) |
| 配额粒度    | 个人       | 租户               |

**四行全部相反。** 那不是一个档的两种配置,是两个产品。

所以那份评估文档的结论(「等工作区语义定清楚之后再回来看」)现在有答案了:
**语义定了,答案是不做。** 该文档状态改为「已关闭」。

⚠️ **省下的内存是真的,放弃它是有代价的** —— 50 人仍然是 50 个进程、约 3.2 GB。
接受这个代价的理由是:**省内存的那个方案要付的是产品语义,而语义比内存贵。**
内存可以加,语义改了要迁移用户数据。

## 与既有实现的关系

好消息是**实现层不用改**:V0.4.1 的四段路径模型
(`{root}/{tenantId}/{userId}/{workspaceId}`)本来就是按这个语义做的。
本决策是把「当时那么做」升级成「明确这么定」,并据此关掉一个悬着的备选方案。

`fs-tenant` 的 `workspaceOf` 回调、`DEFAULT_WORKSPACE_ID`、路径钉死,
全部保持不变。
