# 哨兵默认值冒充「未配置」—— 全仓扫描结果

日期:2026-08-18 · 状态:扫描完成,**两条确认,均未修**(待裁决)

> **起因**:V0.8.0 把 `primaryColor` 从「`string` + 哨兵默认 `#2F6FEB`」改成
> `string | null`。这是同一形状的**第二次**(第一次是 V0.6.0 的发票卖方)——
> **同一个形状很少只出现两次**,所以扫一遍全仓。
>
> 方法:按领域并行扫描 → 逐条**对抗式核实**(默认误报,除非证据确凿)。
> 候选 13 条,**确认 2 条,排除 11 条**。

## 判据(扫描用的,也是将来判新字段用的)

一个字段算「哨兵默认值冒充未配置」,必须**同时**满足:

1. 类型**不可空**(没有 `| null` / `| undefined`)
2. 存在一个特定值被用来表示「用户没配」
3. 因此「用户显式配成这个值」与「用户没配」在**类型层无法区分**

**不算**的:已经是 `T | null` 的;两种状态语义本就相同的;常量与枚举;
以及刻意的 fail-closed 哨兵(那是安全设计不是缺陷)。

## 确认 ①:`costMinorUnits: 0` —— 「没配价」与「本地不计费」折叠成同一个 0

|            |                                                                               |
| ---------- | ----------------------------------------------------------------------------- |
| **位置**   | `packages/metering/src/index.ts:84`(类型)· `:187-198`(折叠点)                 |
| **类型**   | `readonly costMinorUnits: number` —— 不可空,线上契约同样是裸 integer          |
| **哨兵**   | `price === undefined ? 0`                                                     |
| **严重度** | 🔴 **高** —— 它顺着 `LocalBilling.rateLines` 直接进 `InvoiceLine.amountMinor` |

### 碰撞在「缺席」本身,不在「显式配 0」

一个**反直觉的点**,核实时才看清:碰撞面**不是**「有人显式配了 `{0,0}`」——
`GOVERNANCE.md` 明确规定真免费的那类(本地 provider)**不要配价**。
真正的碰撞是**缺席**承载了两个都合法、方向相反的含义:

| 缺席 +        | 含义               | 对不对                             |
| ------------- | ------------------ | ---------------------------------- |
| 本地 provider | 「本地算力不计费」 | ✅ 正确,**且这是被规定的配置方式** |
| 云端 provider | 「忘了配价」       | ❌ 错误 —— **静默少算账单**        |

⚠️ **V0.6.5 的本地例外没有化解歧义,而是把它焊死了**:0 不再是一个
「认真的部署方把表配全就能消灭」的哨兵 —— **教条本身禁止配全**。

### 现有机制兜不住

- `summarizeLocalUsage(records, localProviders)` **知道**哪些 provider 是本地的,
  但它刻意没有金额字段;而 `aggregateDaily` **拿不到这个列表** ——
  判别信息存在于系统里,却到不了产生 0 的那一行
- `assertPayable` 拒 0 元发票,兜住的是**全盘**失配(空价格表 → 全 0)。
  **兜不住部分失配** —— 少配一个云端模型,出来的是一张看起来正常、
  金额偏低的发票,**没有任何一道会红**
- 全仓 grep:这条不变式的唯一执行者是 README / GOVERNANCE 里的**散文**

⇒ **它比已修的两个还弱**:seller 与 primaryColor 至少还是运行时约定,
这个只是文档里的一句话。而**它落在发票的金额栏上**。

### 🚨 一个错误的修法(核实时被否掉,记下来免得有人再走)

**不要**把 `costMinorUnits` 改成 `number | null`。理由两条:

1. **本地行与漏配行会双双变 null** —— 歧义原地换个方向重来一遍
2. `UsageRecord` 在冻结的 `openapi.json` 里是裸 integer,改可空是**破坏性变更**

⚠️ 关键差异:`costMinorUnits` 是**派生输出**,不是**配置输入**。
seller / primaryColor 表达的是**用户意图**,这个表达的是**算出来的钱** ——
所以修法不是「加 null 承载未配置意图」,而是**「让 0 带上出处」**。

### 建议修法(未实施)

在 `DailyUsageRow` 与 `InvoiceLine` 上加一个三态判别字段:

```ts
costBasis: 'priced' | 'unpriced' | 'not-billable'
```

- `priced` —— 价格表命中
- `not-billable` —— 未命中 **且** provider 在本地列表里(GOVERNANCE 规定的正当缺席)
- `unpriced` —— 未命中 **且** 不是本地 → **这才是配置遗漏**

⚠️ **本地 provider 列表必须喂进 `aggregateDaily`。** 少了这一维,
`unpriced` 会给每条本地行都打告警,部署方三天内就学会无视它 —— **那等于没加**。

**配套(按「谁验证它」)**:出票路径遇到 `unpriced` 行就拒绝出票或显式告警,
理由与 `assertSellerConfigured` 同款;并给它一条负向验证 ——
植入一条未配价的云端用量,确认它真的红。

**顺带**:`gateway/src/server.ts:231` 的缺省 `prices: {}` 是同一条歧义在装配层的
另一个入口 —— **空价格表是「还没配」而不是「都免费」**。

### ✅ 已实施(V0.9.0 Session 5.5)—— 与建议的三处差别

落地形状是 `Cost` 判别联合(`packages/metering/src/cost.ts`),
而不是在旧字段旁边加一个 `costBasis`。三处差别值得记下来:

| 建议                                        | 实际                            | 为什么改                                                                                                           |
| ------------------------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 加一个并行字段 `costBasis`                  | **换掉整个字段**:`cost: Cost`   | 并行字段允许 `costBasis: 'unpriced'` 与 `costMinorUnits: 0` 同时存在 —— 歧义还在,只是多了一个字段                  |
| `not-billable` 由**本地 provider 列表**推断 | `unbilled` 由部署方**显式声明** | 推断要把列表喂进 `aggregateDaily`,而「哪些算本地」本身又是一个会分家的清单;声明只有一处,且它是一句**部署方说的话** |
| 只处理语义折叠                              | **顺带修掉单位假设**            | 两者都要改同一个字段的形状,分两次动 = 破坏性变更做两遍,而第二次会发现第一次挑的形状不够用                          |

⚠️ **「不要改成 `number | null`」那条判断经受住了实施**:最终形状确实不是可空数字,
而是一个带 `kind` 的对象 —— 因为要装的是**四件事**
(多少钱 + 什么币种 + 几位小数 + 算不算得出来),`number | null` 只能装两件。

装配层那条也一并修了:`governance.pricing` 缺席不再回落到
`{ currency: 'CNY', prices: {} }`,而是让每一行都成为 `unpriced`。

**谁验证它**:`verify-assertions.mjs` 探针 29(把 `unpriced` 折回零元 → 断言变红)、
`check-guards.mjs` 的「没有人自带币种指数表」+ `verify-guards.mjs` 42a–c。

## 确认 ②:`memberCount ?? 0` —— 把安全警告变成放行

|            |                                                                          |
| ---------- | ------------------------------------------------------------------------ |
| **位置**   | `gateway/src/admin/routes.ts:349`                                        |
| **原文**   | `const memberCount = (await options.memberCount?.(admin.tenantId)) ?? 0` |
| **严重度** | 🟡 **中低** —— 但**形状最典型**                                          |

### 它是 `branding.ts` 点名禁止的那个表达式

> 「禁止 `?? '#2F6FEB'` 之类的兜底:那会把类型层刚区分开的两种状态在
> 第一个调用点重新合并。」

`?? 0` 字面上就是它。碰撞:**「没接线 → 数目未知」 vs 「接了线,租户真的 0 个成员」**。

### 后果不是显示错一个数,是**把警告变成放行**

`console-web/src/capacity-view.ts:30` 按 `memberCount` 分支选**文案**:

| memberCount | 逻辑档下的健康态 | 文案                                                                  |
| ----------- | ---------------- | --------------------------------------------------------------------- |
| 真实 > 1    | `full`           | 「已超出逻辑隔离档的上限。**必须**改用进程隔离」← V0.4.7 静默覆盖警告 |
| 哨兵 0      | `single-user`    | 「逻辑隔离档,只支持一位成员」← **安抚性**                             |

⇒ **哨兵把一条安全警告换成了一句「没事」。**

### 同一文件里,它是唯一一个「静默替代」的可选依赖

`subjectStore` / `usageReader` / `quotaAdmin` / `modelPolicies` / `auditStore` / `capacity`
**全部**是 `undefined → notImplemented()`(501)。只有 `memberCount` 兜了个 0。

而 `routes.ts:88` 的注释写着「与 capacity 成对 —— 缺一个这个端点就没意义」,
**代码只执行了这句话的一半**。测试里有 `omitCapacity` 开关与 501 断言,
**没有 `omitMemberCount`** —— 那条路径从没被任何测试走过。

⚠️ **严重度限定要说清**:`server.ts:513-529` 总是把 capacity 与 memberCount
成对接线,**没有任何已发布的默认部署会撞上它**。它只经公开导出可达 ——
也就是说,**与那条已经被判定值得一个 501 分支和一条测试的 capacity-absent 路径,
可达性完全相同**。

### 建议修法(未实施,两条待选)

**最小**:与同文件惯例对齐 ——

```ts
if (options.capacity === undefined || options.memberCount === undefined)
  throw notImplemented('V0.5.0')
const memberCount = await options.memberCount(admin.tenantId) // 去掉 ?? 0
```

**更彻底**(更贴 `seller.ts` 的先例):把这对合成一个可选对象,让「缺一个」
**在类型上不可表达**,而不只是被运行时拒绝 —— 代价是要动 6 处调用点。

⚠️ 无论选哪条,**都要补上缺失的负向测试**(`omitMemberCount` → 501),
否则新分支没人验证。

**不要**改 `admin.ts:178` 或 `openapi.json` —— 线上字段是 required 的非空整数,
这个案子的正确答案是 501,不是可空。

## 排除的 11 条(不逐条列,记判据)

排除理由集中在三类:

1. **已经是 `T | null`** —— 那正是正确形态
2. **两种状态语义相同** —— 有合理业务默认,「配成该值」与「没配」没区别
3. **刻意的 fail-closed 哨兵** —— 那是安全设计不是缺陷

⚠️ 核实阶段**默认判误报**,不确定就排除。宁可漏报也不要误报 ——
一份充满误报的清单会让人去改本来正确的东西
(这正是 V0.6.5 `session-tasks.mjs check` 假阳性的教训)。

## 这次扫描本身的一条收获

**报告与核实必须分开,而且核实要能推翻报告的举例。**
确认 ① 的核实结论是「**结论对,但举例错**」—— 报告说的碰撞面
(「有人显式配了 0」)不成立,真正的碰撞在缺席本身。
若照报告的举例去修,会修错地方;而核实还**否掉了报告给的两个方案之一**。
