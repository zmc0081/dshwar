## 确认 ①:`markPaid` 说「落进发票与审计」,而审计一次都没写过

|            |                                                                 |
| ---------- | --------------------------------------------------------------- |
| **位置**   | `packages/billing/src/service.ts:89`                            |
| **承诺**   | 「本方法不验证 paymentRef,只把它**原样落进发票与审计**。」      |
| **实际**   | 「落进发票」做了;「落进审计」**在任何实现或调用路径上都不存在** |
| **严重度** | 🟡 中 —— 见下方「活没活」                                       |

### 独立核对(读代码,不凭报告)

- `packages/billing/src/service.ts:89` 原文确实是「原样落进发票与审计」
- `grep audit` 扫 `billing` / `billing-local` / `billing-stripe` 三个包的 `src`:
  **零个 import、零次写入**(只剩两处「与 audit 同款理由」的行文类比)
- 调用侧也没有:`processStripeEvent` 成功记账后只 `processed.record(event.id)`;
  网关的 webhook 端点只有**验签失败**的 `onRejected`,成功路径直接返回 200

⇒ **「钱到账、发票从 issued 变 paid」这件最该有时间线的状态变更,审计里一条都没有。**

### 它不是明写的缺口

本项目明写缺口时有固定长相(`api-contract/src/billing.ts:5` 明确推后「发票的
查询与管理端点」;`gateway/src/admin/audit.ts:31` 写「V0.3.0 换成 @dshwar/audit
的实现」)。**这一处没有任何缺口标记** —— 它是以陈述句写的。

### 「活没活」要说清

`gateway/src/server.ts` **从不装配 billing、从不传 billingRoutes**,
于是 `app.ts` 落到 `stripeWebhookFailClosed()` —— **出厂网关对该 webhook 无条件 401**。

⇒ 它误导的是**自建者**:按文档用导出的 `registerStripeWebhook` 接支付的那些部署,
确实会拿到「发票转 paid 而审计零记录」。

⚠️ 顺带(同味道,价值更低):`packages/billing/src/gateway.ts:13` 把
`PaymentHandle.provider` 记作「审计与对账用」,同样没有任何代码把它喂进审计。

### 建议(二选一,选完让注释与实现对齐)

**(a) 改注释** —— 与契约「不读 ctx」的设计一致:说明 `markPaid` 只把
paymentRef 记到发票上,**记进审计是调用方的义务**;并把这条义务写进
`gateway.ts` 的「实现方职责」清单(今天那里有三条,没有审计这条)。

**(b) 真做** —— 加在**唯一的真实接缝**上而不是账本里面:
`ProcessInput` 上加 `onApplied?`,在 markPaid 成功后触发,由网关侧
与既有的 `onRejected` 一起接进同一个 AuditSink。

⚠️ 选 (b) 就要按「谁验证它」配验证:断言 'applied' 路径**恰好**收到一条记录,
**以及** 'duplicate' / 'already-paid' 路径**保持为空** —— 否则重复记账的回归看不见。

## 确认 ②:`MeteringStore.query` 写死「按 at 升序」,两个实现只有一个兑现

|            |                                                                 |
| ---------- | --------------------------------------------------------------- |
| **位置**   | `packages/metering/src/index.ts:96`(接口)· `:108`(不兑现的实现) |
| **承诺**   | 「原始明细,**按 at 升序**。」—— 写在接口方法上的行为断言        |
| **实际**   | `InMemoryMeteringStore.query` 返回 **push 顺序**,一次排序都没有 |
| **严重度** | 🟢 **休眠** —— 见下                                             |

### 独立核对

| 实现                    | 行      | 做了什么                   | 兑现?             |
| ----------------------- | ------- | -------------------------- | ----------------- |
| `InMemoryMeteringStore` | 108-114 | `this.records.filter(...)` | ❌ **push 序**    |
| `KvMeteringStore`       | 144-146 | `Object.keys().sort()`     | ✅ 字典序即时间序 |

`KvMeteringStore` 的 `record` 处(137 行)还专门注了「字典序即时间序」——
说明作者对这条性质**是有意识的**,只是内存实现漏了。

**同一个接口的两个实现,在一条写死的保证上行为不同。**

### 为什么判「休眠」而不是「高危」

今天没有任何代码路径会撞上它:

- 唯一的生产接线(`server.ts` 用 `InMemoryMeteringStore`)在取 `at` 后**同步 push**,
  push 序恒等于时间序
- 三个消费方全部与顺序无关:`policy.usedInPeriod` 按区间 filter、
  `billing-local` 的 `rateLines` 按金额重排、网关 usage 走 `aggregateDaily` 按日期重排

**激活它需要**:一个乱序写入方,或一个「按注释直接取首尾条当周期边界」的消费方。
仓库里都不存在 —— 但注释正**邀请**后者。

### 建议

一行修:`InMemoryMeteringStore.query` 加 `.sort((a, b) => a.at.localeCompare(b.at))`。

⚠️ 按「谁验证它」,修完要有一条测试盯着:**乱序 record 两条,断言 query 返回升序** ——
而且这条测试要**对两个实现都跑**(参数化跑 `InMemoryMeteringStore` 与
`KvMeteringStore`),否则下一个实现照样可以不兑现。

> 这与 V0.8.0「三种语言各验一次」是同一条:**一个接口有几个实现,
> 那条保证就要被验几次。**

## 🚨 确认 ③:契约说 `/v1/jobs` 已实现,而实现根本不存在 —— 出厂 404

|            |                                                                   |
| ---------- | ----------------------------------------------------------------- |
| **位置**   | `packages/api-contract/src/routes.ts:504 / 518 / 532`             |
| **承诺**   | 三条 `status: 'implemented'`(`listJobs` / `createJob` / `getJob`) |
| **实际**   | `gateway/src/jobs/` 里**只有 `store.ts`**,一个 handler 都没有     |
| **严重度** | 🔴 **高** —— 而且它已经流到了对外产物                             |

### 它踩的是 `workbench.ts` 自己写死的那句话

`packages/api-contract/src/workbench.ts:12-16`:

> 未实现的端点返回 **501 而非 404**……404 会让第三方以为路径写错、
> 去猜别的路径;501 说的是「这个端点是真的,只是还没到」。

而 `/v1/jobs` **正好返回 404** —— 因为 501 兜底那个循环只覆盖
`status === 'planned'`(`gateway/src/admin/routes.ts:563`:
`if (route.status !== 'planned') continue`)。

⇒ **标错 status 的代价不是「文档不准」,是它把这条路由从 501 名单里踢了出去。**
`planned` 会被兜住,`implemented` 不会 —— 于是一条谎报为已实现的路由,
拿到的恰恰是那句注释点名要避免的 404。

### 实测(复刻 `server.ts` 的接线,含 `adminRoutes`)

| 路径              | 契约 status   | 实际                     |
| ----------------- | ------------- | ------------------------ |
| `/v1/jobs`        | `implemented` | **404 `not_found`**      |
| `/v1/jobs/{id}`   | `implemented` | **404 `not_found`**      |
| `/v1/attachments` | `planned`     | 501 `not_implemented` ✅ |

**对照组是关键**:`attachments` 证明 501 机制本身是好的 ——
坏的只有 status 标错的那几条。

### 还有一处让人以为它接过线

`gateway/src/app.ts:111-112` **给 `/v1/jobs` 挂了 `runtimeAuth` 中间件**。
给一组不存在的 handler 配了鉴权 —— 说明写的时候确实以为它们在。

### 它比前两条严重,因为它已经出厂

`status` 进 `openapi.json`,而 V0.8.0 刚用同一份 `openapi.json`
生成了 **TS / Kotlin / Swift 三种 SDK**。
⇒ TS 产物里 `listJobs` / `createJob` / `getJob` 三个 **operation 类型**在,
第三方按它生成客户端就会调出 404。
⚠️ 但**没有任何 SDK 生成过方法** —— 详见下方「处置结果」的订正。

### 建议(二选一)

**(a) 改标 `planned`(最小、可逆、与事实一致)** —— 三条改成
`status: 'planned'` + `plannedVersion`,它们立刻落进 501 兜底,
SDK 里也会带上 planned 标记。**推荐**:契约的 status 字段说的是
「实现到哪了」,把它改成真话不需要任何裁决。

**(b) 写 handler** —— `InMemoryJobStore` 已经在,但作业执行语义
(排队、取消、与 session 的关系)没定,属于新功能,不是修 bug。

⚠️ 无论哪条,都要按「谁验证它」补一道守卫 —— 见下方 ④ 的建议,两条共用一道。

## 处置结果(2026-08-21,V0.8.0)

|                          | 结论             | 处置                                                          |
| ------------------------ | ---------------- | ------------------------------------------------------------- |
| ① `markPaid` 审计        | 真做             | `ProcessInput.onApplied` 接缝 + 网关接进 AuditSink;探针 20/21 |
| ② `query` 排序           | 一行修           | 字典序 sort;测试进已有参数化 describe,两个实现各验一次        |
| ③ `/v1/jobs` 标错        | 改标 `planned`   | 三个 SDK 实测纯增量,非破坏性                                  |
| ④ `workbenchRoutes` 漏接 | 接上             | 刻意不传 `policies`,见下 ⑥                                    |
| ★ 根                     | 出厂装配无人核对 | `gateway/test/shipped-assembly.test.ts` + 探针 19             |

### ③ 的实测:改 status 到底动了什么

用户问的是二选一(「仍生成方法 → 不变」还是「不生成 → 少三个方法」)。
**实际是第三种**,两个分支都不成立:

| SDK            | 生成什么                                                                      | 改 status 后      |
| -------------- | ----------------------------------------------------------------------------- | ----------------- |
| Kotlin / Swift | **只从 `components.schemas` 生成数据模型**(经 `model-ir.ts`,它从不读 `paths`) | **字节不变**      |
| TypeScript     | 经 openapi-typescript,`paths` + `operations` + schemas 都进产物               | **+33 行,0 删除** |

关键事实两条:

1. **没有任何 SDK 生成过方法。** TS 的 `DshwarClient` 六个方法全是手写的
   (会话 ×5 + 流),`listJobs` / `createJob` / `getJob` **从来不存在**。
   ⚠️ 本文件此前写着「四种语言的客户端都有这三个方法,调用全部 404」——
   **那句话是错的**,而且错在两处:SDK 是三种不是四种(无 Python SDK),
   方法根本不存在。已订正。
2. **`x-dshwar-status` 不进任何产物** —— openapi-typescript 丢弃 operation 级的
   未知 `x-` 扩展。TS 产物里那 33 行来自 `responses` 里**手写的 501 声明**,
   不是从 status 派生的。所以「改 status」本身对 SDK 是**零影响**;
   有影响的是配套加的 501 条目,而那是纯加法。

⇒ 结论:**不是 SDK 层的破坏性变更,不需要单独声明。** 行为 404 → 501 是改善。

`GET/PATCH /v1/workspaces/{id}/policy` 会开始接受写入并把策略存下来 ——

⇒ 不传 `policies` 让这两个端点回落 501,与 `routes.ts:42-44` 的原话一致:
「缺席**不等于放行** —— 它意味着这个部署没接策略层」。

**待裁决**:把 enforcer 接进 agent 的工具调用路径,是一件真功能

## 🚨 确认 ⑥:契约冻结检查从不看 `responses` —— 换掉响应体它报「契约未变」

|            |                                                                          |
| ---------- | ------------------------------------------------------------------------ |
| **位置**   | `packages/api-contract/src/freeze.ts:68-77` `diffContract`               |
| **承诺**   | 门禁输出的那句「破坏性 N 处」,全项目当它是兼容性的权威判定               |
| **实际**   | 它只比 **paths 增删 · operation 增删 · parameters · components.schemas** |
| **严重度** | 🔴 高 —— 它是**我在这一轮里正拿来给用户下兼容性结论的那个工具**          |

### 实测(植入 → 跑真实脚本 → 还原)

把 `GET /v1/sessions` 的 200 响应体从 `ListSessionsResponse` 换成
`ErrorResponse` —— 对已接入客户端**最大级别**的破坏:

```
差异: 破坏性 0 处,相容 0 处
契约未变。
退出码=0
```

### 为什么这个洞能活下来:负向验证只验了四个维度里的一个

`verify-guards.mjs` 的 8 号负向验证**删掉一整条 path**(`/v1/sessions/{id}/turns`),
确认门禁变红。它证明的是**门禁接线是通的**,不是**分类器覆盖了变更空间**。
而它的绿,读起来就是「契约冻结检查已验证」。

⇒ **这是「谁验证它」的第七次,而且是一个新的子形状**:

> 一个**多维分类器**,负向验证只走通其中一维,
> 那条绿会被读成「整个分类器已验证」。

与「一条探针一个目标」同源(红是「或」),但方向相反:
那条说的是**多目标掩盖空跑**,这条说的是**单维掩盖未覆盖的维度**。

### 不要误伤:有一处「不设防是正确的」是真的

`routes.ts:258-260` 写着「只有 `x-dshwar-status` 扩展消失,契约冻结检查
对此不设防是正确的:『planned 转实现』正是契约先行策略承诺过会发生的事」。
**那句话成立**,且正是本次 ③ 依赖的判据。
⑥ 说的是另一件事:**`responses` 里的 `$ref` 换掉**与扩展字段变化毫无关系。

### 建议(**已实施** —— 见文末「⑥ 的处置」)

给 `diffContract` 补 responses 维度,至少三条:

| 变更                          | 分类                                 |
| ----------------------------- | ------------------------------------ |
| 2xx 响应的 schema `$ref` 改变 | **breaking**                         |
| 已声明的响应码被删除          | **breaking**(客户端可能在分支处理它) |
| 新增响应码(如本次的 501)      | additive                             |

⚠️ 配套按「谁验证它」:**每加一个 `ContractChangeCode`,
`verify-guards.mjs` 就要多一条植入那种变更的负向验证** ——
否则新维度会重复今天这个洞。这条应该写成规则,不是一次性动作。

## ⑥ 的处置(2026-08-21,单开 Session 完成)

### 洞比「responses 一个维度」大得多

逐条植入 15 种真实的破坏性变更实测(每例都先断言变异真的改到了文档),
**8 种漏报**:

| 漏报的变更                                  | 根因                                     |
| ------------------------------------------- | ---------------------------------------- |
| 响应体 `$ref` 换成不相干的类型              | `diffContract` 不遍历 `responses`        |
| 删掉已声明的响应码(200 / 404)               | 同上                                     |
| 请求体 schema 换掉                          | `requestBody` 也不遍历                   |
| **`components.schemas` 内部**的 `$ref` 换掉 | `JsonSchema` 接口里**没有 `$ref`**       |
| `anyOf` 分支改类型 / 收窄                   | `anyOf`/`oneOf`/`allOf` 声明了却从不比对 |
| operation 的 `security` 改掉                | 不在遍历范围内                           |

⚠️ 第四行最刺眼:**`components.schemas` 恰恰是大家默认「已经覆盖了」的那一维**,
而本仓用 `$ref` 表达一切跨类型引用 —— 那一维只覆盖了它自己的一半。

### 补了五个分类码,现在 15/15

`schema.ref.changed` · `schema.union.changed` · `response.removed` ·
`response.added` · `operation.security.changed`

判定策略沿用本文件既有的那条:**同一个 schema 既可能在请求侧也可能在响应侧,
方向相反,按更保守的一边判**(与 `property.required.added` / `.relaxed` 同款)。

### ★ 追溯逼出了两条豁免 —— 而它们是规则的 bug,不是历史的 bug

用户要求「补完之后拿当前契约与 V0.2.0 首冻基线比一遍」。做了两遍:
**累计**(V0.2.0 → 当前)与**逐提交两两比**(21 步全走)。

**累计有两个盲区,逐对没有**:

1. 中途破坏、后来又改回来的,首尾看不见;
2. **基线之后才新增的路径** —— 首尾只报 `path.added`,其响应体从不参与比较。

第一版规则在这两遍里报了两批「破坏性」,**全部是规则自己的误报**:

| 批                | 报了什么                                   | 真相                                                             | 修法                                                                |
| ----------------- | ------------------------------------------ | ---------------------------------------------------------------- | ------------------------------------------------------------------- |
| 累计,8 处         | Admin 端点的 501 被删                      | 全是 `planned → implemented`,而那是契约先行策略**承诺过**的收缩  | 豁免:`x-dshwar-status` 由 planned 变 implemented **且**删的就是 501 |
| 逐对第 16 步,8 处 | `/v1/admin/capacity` 的 200 响应体整块变了 | 内联结构提取成 `$ref: Capacity`,**解引用后逐字节相同** —— 纯重构 | `$ref` 与内联互比时先解引用,再按结构比                              |

⚠️ 第二批只有逐对能看见(capacity 在 V0.2.0 根本不存在)。
**所以「补完规则要追溯」还得加一句:逐步走,不能只比首尾。**

⇒ 顺带订正一处旧注释:`routes.ts` 在 `listSubjects` 上写着转正时
「**只有** `x-dshwar-status` 扩展消失」—— 那句话不完整,501 也一起消失了。
它当时之所以没被发现,正是因为分类器看不见 `responses`。

### 追溯结论:八个版本的「破坏性 0 处」经得起新分类器

| 口径                    | 结果                                               |
| ----------------------- | -------------------------------------------------- |
| 累计 V0.2.0 首冻 → 当前 | **破坏性 0 处,相容 40 处**(旧分类器只看得见 32 处) |
| 逐提交 21 对全走        | **破坏性合计 0**                                   |

**它们此前不是错的,是没被验证过的。现在验过了。**

### 负向验证:从 4 条散装改成 19 条表驱动

此前是四条手写(`path.removed` / `enum.value.removed` + 两条相容侧对照)——
**十四个分类码里的四个**。现在 `verify-guards.mjs` 里是
`8/9 [<code>]` 一族:**一个分类码一条**,各自植入一次真实变更、
跑一次真实门禁(0.16s/次)、断言退出码与输出里的码。

★ 关键是末尾那条**完备性断言**:码表从 TS 源里**现取**(子进程带 strip-types),
与负向验证表比对,**少一个码就红并点名它**。
负向验证过一次:往 `CONTRACT_CHANGE_CODES` 里塞一个没有条目的码 →
`失败 8/9 每个 ContractChangeCode 都有一条负向验证(完备性)
这些分类码没有负向验证:zz.probe.newcode`。

没有这一条,表会重新退化成「写到哪算哪」—— 而那正是它要替换掉的东西。
