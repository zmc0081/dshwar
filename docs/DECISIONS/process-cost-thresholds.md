# 决策:进程隔离代价的 CI 阈值怎么定

> **状态**:✅ **已实测并接入门禁**(2026-08-16)。
> 脚本:[`scripts/measure-process-cost.mjs`](../../scripts/measure-process-cost.mjs) ·
> CI job:`进程隔离代价(Linux 基线)`

## 为什么需要一道门禁,而不是一次测量

V0.4.5 在 Windows 开发机上量到 **~115 ms 冷启动 / ~58 MB 常驻**。这两个数随后
被三处引用,而**采用者照着它们买服务器**:

| 引用处                                       | 引用的是什么                       |
| -------------------------------------------- | ---------------------------------- |
| `README.md` 的规模对照表                     | 5 / 20 / 50 / 200 人分别要多少内存 |
| `gateway.config.example.json` 与 `profiles/` | `maxProcesses` 的默认值            |
| `docs/DEPLOYMENT.md`                         | 容量规划一节                       |

**一次让常驻内存翻倍的改动会让这三处同时变成谎话** —— 比如给子进程多装一个插件、
换一个更重的依赖、或者上游某次升级自己变胖了。而这类回归**不会让任何测试变红**:
内存不在任何断言里。所以它必须是常驻门禁。

## 口径:必须与 V0.4.5 那次可比

否则 Linux 与 Windows 的差异分不清是**平台差异**还是**测法差异** —— 而那正是
这次复测要回答的问题。三条对齐:

1. **五次采样,全部保留、全部报告。** 不丢弃第一次(V0.4.5 也没丢)。
   第一次通常最慢,丢掉它数字更好看,但那是另一个口径。
2. **冷启动由父进程侧墙钟测量**(`fork()` → 收到 `ready`)。
   ⚠️ V0.4.5 踩过的坑:子进程内 `Date.now() - t0` 量出来只有 10 ms,**差十倍** ——
   ESM 的 import 在模块体执行之前就求值完了,那个数不含进程创建与模块加载。
3. **同一个子进程夹具**,装配全部 11 个插件。少装几个数字偏乐观。

### 口径已验证:新脚本能复现 V0.4.5 的数

在同一台 Windows 机器上跑新脚本,对照 V0.4.5 手工测的那组:

| 量       | V0.4.5 手工(Node 22) | 新脚本(Node 24)      | 判断      |
| -------- | -------------------- | -------------------- | --------- |
| 插件装配 | 12–14 ms             | 12–13 ms             | ✅ 一致   |
| 冷启动   | 115–128 ms           | 118–176 ms(中位 127) | ✅ 同区间 |
| 常驻 RSS | 57–58 MB             | 54–55 MB             | ✅ 相近   |

**这一步不能省。** 不先证明新脚本能复现旧数,Linux 上量出来的任何差异都无法归因。
RSS 略低与冷启动的那个 176 ms 离群点,分别由 Node 版本与调度抖动解释 ——
后者正是下面取中位数的理由。

## 判据取中位数,不取均值

GitHub 的共享 runner 是吵的:一次调度抖动能让单次采样接近翻倍(上表的 176 ms
就是本地机器上的同类抖动)。均值会被那一次拖走,中位数不会。

**这道门禁要抓的是「改动让代价翻倍」,不是「今天这台机器忙」。**
后者的红没有信息量,而没有信息量的红会训练人去忽略它 —— 那比没有门禁更糟。

## 阈值的定法

**阈值 = 实测中位数 × 系数**,两个维度的系数刻意不同:

| 维度         | 系数    | 理由                                                                                                   |
| ------------ | ------- | ------------------------------------------------------------------------------------------------------ |
| **常驻 RSS** | **1.5** | 内存是**稳的** —— 上表五次采样跨度只有 1 MB。1.5 倍足够宽,而一次翻倍(2.0)会被稳稳抓住                  |
| **冷启动**   | **2.5** | 时间是**吵的** —— 同一台机器上就有 118→176 的抖动(1.5 倍)。系数必须容得下 runner 噪声,否则它会随机变红 |

⚠️ **冷启动的 2.5 倍意味着它抓不到「慢 2 倍」的回归,只抓得到「慢 2.5 倍以上」。**
这是清醒的取舍,不是疏忽:一道会随机变红的门禁最终会被加 `continue-on-error`,
那时它一条也抓不到。**内存那条才是主力**,而内存恰好是三处文档里更要紧的那个 ——
`maxProcesses` 的默认值由它决定,冷启动只影响体验。

## 首次接入刻意分两步

**第一次跑不带 `--assert`,只测量。** Linux 的阈值必须由 Linux 上的实测推出,
而不是照 Windows 的数猜一个 —— 猜一个宽松阈值即使绿了也没验证任何东西,
它只证明猜得够松。拿到数之后按上表的系数算,再换成带 `--assert` 的版本。

## Linux 基线(2026-08-16 实测)

GitHub `ubuntu-latest` · Node v22.23.2 · 5 次采样中位数:

| 量       | Linux 实测 | 系数 | 阈值       |
| -------- | ---------- | ---- | ---------- |
| 冷启动   | **86 ms**  | 2.5  | **215 ms** |
| 常驻 RSS | **63 MB**  | 1.5  | **95 MB**  |
| 插件装配 | 16 ms      | —    | 不判定     |

Windows 同日复测(Node 24)为 **127 ms / 55 MB**,阈值 **318 ms / 83 MB**。

### ★ 结果里有一条与预期相反的

| 量       | Windows | Linux     | 差异     | 预期                 |
| -------- | ------- | --------- | -------- | -------------------- |
| 冷启动   | 115 ms  | **86 ms** | **−25%** | ✅ 符合(fork 更便宜) |
| 常驻 RSS | 58 MB   | **63 MB** | **+9%**  | ❌ **反了**          |

`FEASIBILITY-REPORT-V45.md` §6 与 `README.md` 都写着「Linux 上 fork 更便宜,
预期更低」。**那句话只对了一半**:冷启动确实降了四分之一,但**常驻内存反而高了
5 MB**。两者本来就由不同机制决定 —— 冷启动看进程创建与模块加载,常驻看堆与
运行时开销,glibc 的 malloc arena 行为与 Windows 的堆管理器不同,没有理由同向。

**把两个量绑在一句「Linux 更便宜」里,是这次复测纠正的实质错误。**

后果落在容量规划上,而且方向是**低估**:按 58 MB 算的规模对照表,在真实的
Linux 生产环境上每个进程少算 5 MB。50 人 ≈ 2.9 GB → 实际 **≈ 3.2 GB**。

⚠️ **`maxProcesses: 64` 的默认值本次不动** —— 那是产品决策,留给仓库所有者
看着数据定。可供参考的算术:64 × 63 MB ≈ **4.0 GB**(原按 58 MB 算是 3.7 GB)。
本文档只负责让差异**被发现**,不负责替人做决定。

## 放宽阈值 = 关掉这道门禁

阈值放宽一次,它就再也抓不到下一次翻倍。超阈值时的正确顺序是:

1. 查清是哪个改动导致的
2. 如果代价是**有意接受**的 —— 同步更新 README 规模对照表、`maxProcesses`
   默认值、DEPLOYMENT.md 容量规划**这三处**,然后才动阈值
3. 只有在确认是测量环境变化(换 runner 规格、换 Node 大版本)时,才单独调阈值

脚本失败时会把这三处直接打印出来,免得漏改。
