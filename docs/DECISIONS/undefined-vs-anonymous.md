# 评估:把「绑定缺失」与「合法匿名」分开

> **状态**:🟡 **仅评估,未实现,未排期**(V0.5.5,2026-08-16)。
> **结论**:**可行,而且值得做 —— 但有一个前置条件必须先满足**,
> 否则改了之后会把单用户部署打挂。

## 问题

`PrincipalService.current()` 今天是这样:

```ts
current(): Principal {
  const bound = this.ctx.get(PRINCIPAL_BINDING) as Principal | undefined
  return bound ?? ANONYMOUS
}
```

于是 `undefined` 被**无声地**折成 `ANONYMOUS`,而这两者的含义完全不同:

| 情形                              | 今天的表现  | 应该怎样        |
| --------------------------------- | ----------- | --------------- |
| 单用户部署,本来就只有一个人       | `ANONYMOUS` | ✅ 对的         |
| **中间件漏挂**,请求根本没经过认证 | `ANONYMOUS` | 🚨 **应该抛错** |

第二行是 V0.5.5 Session 1 真实发生过的:`/v1/workspaces/*` 的认证中间件
漏了两行,未认证请求拿到 200。当时 `c.get('principal')` 是 `undefined`,
而**归属判定全建立在它之上** —— 等于所有人共用一个匿名身份。

那次是靠一条新写的「认证覆盖」测试抓到的。**问题是那条测试也可能被漏写** ——
下一个新增路由的人未必想到要去补它。

## 核心障碍:今天 `undefined` 真的分不出来

⚠️ **这是本评估最要紧的一条,先说清楚再谈方案。**

单用户部署(`profiles/single-user.yml`)下,**没有任何人 provide 那个槽位** ——
`ctx.get(PRINCIPAL_BINDING)` 返回 `undefined`,而那正是 `ANONYMOUS` 该出现的场合。

换句话说,`undefined` 今天**同时**意味着:

1. 「这个部署只有一个人,不需要身份」—— 合法
2. 「有人忘了挂中间件」—— 配置错误

**在槽位层面它们是同一个值,分不出来。** 直接把 `current()` 改成
「`undefined` 就抛」会让全部单用户部署在第一个请求上崩掉。

## 方案:让「缺失」变成显式的

判据换一个方向 —— 不问「有没有绑定」,问**「装配时有没有人表过态」**:

```ts
// 装配阶段一律 provide 一个值,单用户档也不例外
ctx.provide(PRINCIPAL_BINDING, options.principal ?? ANONYMOUS)
```

这样之后:

| `ctx.get(PRINCIPAL_BINDING)`  | 含义                                    | `current()`      |
| ----------------------------- | --------------------------------------- | ---------------- |
| 一个真实 principal            | 请求经过了认证                          | 返回它           |
| `ANONYMOUS`(**显式** provide) | 单用户部署,装配时表过态                 | 返回 `ANONYMOUS` |
| `undefined`                   | **没人表过态** —— 装配没跑,或中间件漏挂 | 🚨 **抛**        |

**关键在于「显式」二字**:单用户档从「什么都不做」变成「明确地 provide 匿名」。
一个字面上的动作,把一个二义的状态拆成了两个。

⚠️ 这与 V0.4.7 的做法一脉相承 —— 那次也是靠**在根上 provide** 把
「principal 到不了 agent 执行层」解决的。同一个机制,再用一次。

## 影响面(实测清点)

**消费点 13 处**,其中产品源码 4 处:

| 包                      | 用途                                                             |
| ----------------------- | ---------------------------------------------------------------- |
| `credentials-multiuser` | 解析凭据 —— 已经 fail closed(拿不到就没有凭据)                   |
| `fs-tenant`             | 解析工作区根 —— 🚨 **不 fail closed**,老老实实往 `anonymous/` 写 |
| `storage-scoped`        | 存储作用域 —— 同上                                               |
| `principal` 自身        | 服务实现                                                         |

其余是 `dist/` 与类型声明,不算调用点。

**`fs-tenant` 那一行是这次改动的全部价值所在** —— 它是唯一一个
「拿到 ANONYMOUS 也照常干活」的消费方,而它干的活是**决定文件写到哪**。

### 改动清单

1. `PrincipalService.current()` —— `undefined` 抛 `PrincipalUnboundError`
2. `gateway/src/runtime.ts` 的 `assembleRuntime()` —— 无条件 provide
3. `profiles/single-user.yml` 的文档 —— 说明为什么显式 provide 匿名
4. **测试夹具**:凡是裸建 `new Context()` + `PrincipalService` 然后直接调
   `current()` 的,都要补一次 provide

第 4 条是工作量的大头,也是**唯一有可能引入回归的地方** ——
但它的失败形态是「测试红」,不是「生产静默出错」,这个方向是对的。

## 还有一个洞它补不上

⚠️ **Admin 端点不走 `runWithPrincipal`。**

`adminAuth` 中间件设置的是 Admin 身份,不是 principal ——
所以 Admin 路由下 `current()` 会拿到装配时那个根绑定,
而不是「这次请求是谁」。改成抛错**不会**让这一点变好:
它本来就不该在 Admin 路径上被调用。

⇒ 这个方案解决的是「运行时端点漏挂中间件」,**不解决**「Admin 端点误用
principal」。后者需要另一条守卫(或让 Admin 上下文根本没有那个服务)。
不要指望一个改动补两个洞。

## 建议:**V0.6.0 Session 0 做**(排期已修正)

> ⚠️ **本节原本写的是「排在 V0.6.5 之后」,理由被实测推翻了。**
> 原文与推翻它的数据都保留在下面 —— 这正是
> [`unverified-plausible-causation.md`](unverified-plausible-causation.md) 说的那类错误,
> 而且是我自己犯的第四例。

### 原来的理由(**错的**)

> 「它动的是所有消费方脚下的地基,而当前四个版本连跑期间,
> 每一版都在往上加新的消费方(工作区、作业、附件)。
> 在地基上动手的最佳时机是加完这一批之后,那时消费点清单才是稳定的。」

### 推翻它的两条

**一、这句话反过来读才对。** 若每一版都在加消费方,那么**越晚做爆炸半径越大** ——
「等清单稳定」只在改动是**逐消费方**的时候成立。而本改动在**装配点**,
编辑量不随消费方数量增长,增长的只有出错影响面。(所有者指出)

**二、更要命的是那个前提本身就是假的。** 实测(2026-08-16,真做一遍再还原):

|                                     |                                                                        |
| ----------------------------------- | ---------------------------------------------------------------------- |
| 试改后红掉的测试                    | **15 条 / 4 个文件**                                                   |
| 红掉的是哪些包                      | `fs-tenant` · `credentials-multiuser` · `principal` · `storage-scoped` |
| **V0.5.5 新增的三个消费方红了几个** | **0**                                                                  |

`gateway/src/workspaces/*` · `gateway/src/jobs/*` · `packages/attachment-tenant/*`
里 `principal.current()` 的出现次数是 **0** —— 它们全都**把 principal 当参数收**,
根本不读 ctx。

⇒ **真正受影响的是「读 ctx 的消费方」,而那个集合自 V0.4.x 起就稳定在 4 个。**
V0.5.5 加了三个消费方却一个都没进这个集合。「等它稳定」等的是一个
**已经稳定了的东西**。

### 实际工作量(实测,不是估算)

15 条红全部是**裸建 `new Context()` + `PrincipalService` 而没有根 provide** 的测试,
且集中在各文件的 setup 辅助函数里 —— `packages/principal/test/service.test.ts`
那 7 条共用同一个 helper,**改一行**。

⇒ 装配点 2 行 + 4 个 setup helper。**这个量与「等两个版本」的风险不成比例。**

### 一个必须一起想清楚的语义

⚠️ 「作用域结束后 `current()` 返回什么」。

改动之后,`runWithPrincipal` 回调结束、绑定解除时,`ctx.get` 会**回落到根绑定** ——
而根绑定在改动后**一定存在**(单用户档是 `ANONYMOUS`)。所以作用域退出
不会抛,它拿到的是根上那个值。**这正是想要的**:作用域结束不是错误。

真正会抛的只剩一种:**根上从来没人 provide 过** —— 装配没跑,或中间件漏挂。
