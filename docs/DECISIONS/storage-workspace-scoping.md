# `storage-scoped` 是否需要工作区维度

> V0.4.1 Session 1 · R5 · 2026-08-16
> **结论:不加。** 保持租户维度前缀,工作区维度**不进** `storage-scoped`。

---

## 问题

Session 0 把 `fs-tenant` 的路径改成了四段
(`{root}/{tenantId}/{userId}/{workspaceId}`)。对称的问题随之出现:
`storage-scoped` 的记录键前缀是不是也该加一层工作区?

任务书明写「**若结论是不需要,说明理由,不要为了对称而加**」。以下是理由。

---

## 结论:不加

### 理由一:我们不知道哪些数据属于工作区

`storage-scoped` 包装的是上游 `StorageBackend`,unit 名与记录键**全部来自上游插件**,
对我们是不透明的。同一个 KV 里可能同时存着:

| 数据                     | 正确的作用域                   |
| ------------------------ | ------------------------------ |
| 用户的模型偏好、界面设置 | **用户级** —— 换工作区不该重置 |
| 某个项目的文件索引、缓存 | **工作区级**                   |
| 技能的安装状态           | 租户级或用户级(取决于产品决策) |

加一层工作区前缀是**一刀切**:它会把上面第一类数据也切开。后果是用户新建一个
工作区,发现自己的偏好设置全没了 —— 而这不是 bug 报告里会写清楚的现象,
是「感觉怪怪的」。

**能分清的时候才分。分不清就别切**,这与 `fs-tenant` 的情况正相反:
那里每一个字节都明确属于某个工作区的文件树。

### 理由二:真正要防的风险已经防住了

`storage-scoped` 存在的理由是**跨租户泄漏**——A 公司的人读到 B 公司的记录。
那条已经由租户前缀封死,并有长度前缀防伪造(`encodeKey`)。

同一用户的两个工作区之间**不是信任边界**:它们属于同一个人。V0.4.1 给
`fs-tenant` 做工作区隔离,目的是**组织**(按项目分区干活),不是**安全**——
CLAUDE.md 第七节新增的那条写得很清楚:「同一用户的不同工作区之间也是隔离的,
但隔离级别与租户间相同」,而逻辑隔离本来就仅适用于互相信任的场景。

拿一个组织需求去改一个安全组件,是把两件事混在一起。

### 理由三:作用域在 `open()` 时定格,加工作区会改变契约形状

`scopedBackend(ctx, inner)` 的作用域在 `KvFacet.open()` 那一刻定格
(见 `storage-scoping.md` 的补充节)。要加工作区维度,`open()` 时就必须知道
当前工作区 —— 而 `open()` 往往发生在插件启动阶段,那时还没有任何请求作用域。

这不是实现难度问题,是**时机根本对不上**。硬做的话只能把工作区塞进 unit 名,
而 unit 名会变成文件名与 SQL 标识符,受 `UNIT_NAME_RE` 约束,还会让所有租户的
schema 不再共享 —— 代价远超收益。

---

## 什么时候会推翻这个结论

出现**明确属于工作区**且**必须隔离**的存储需求时。目前已知的候选:

- V0.5.5 工作台后端的「作业状态外置」——那批数据天然属于工作区
- 工作区级的产物索引

那时正确的做法**不是**给 `storage-scoped` 加一刀切前缀,而是:

> 为那个具体的 unit 提供 **opt-in 的工作区作用域**,由使用方在 `open()` 时
> 显式声明「这个 unit 是工作区级的」。默认仍是租户级。

opt-in 与一刀切的区别是:前者出错时影响一个 unit,后者出错时影响全部数据。
