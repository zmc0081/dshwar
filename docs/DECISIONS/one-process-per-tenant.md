# 评估:一租户一进程(而非一用户一进程)

> **状态**:🔴 **已关闭,不做**(V0.5.0,2026-08-16)。
>

> 目标客户要的是团队共享工作区,还是每人私密工作区?」
>

> **每用户多工作区,工作区是项目容器,不跨用户共享。**

> 工作区归属、计量归属、配额粒度、`userId` 段的含义,四项全部相反。
> 那不是一个档的两种配置,是两个产品。**所以不做。**

## 动机

V0.4.7 之后多租户只剩「一 principal 一进程」一条路:50 人 ≈ 2.9 GB。

但隔离需求是**分层的**:

- **跨公司**是硬要求 —— 合同与合规都压在这一层
- **同公司内用户之间**软得多 —— 那才是「互相信任」真正适用的场景

那么:一租户一进程行不行?进程内在根上 provide 一个带正确 `tenantId`、
`userId` 为约定哨兵值的 principal,所有 agent 落到 `{root}/{tenant}/<哨兵>/default/`。
跨公司隔离是真的(进程 + 路径双重),同公司用户共用工作区。
50 人公司从 50 进程变成 **1 进程**。

## 四项技术评估(实测)

### ① `fs-tenant` 的白名单会不会拒掉哨兵 userId

**不会拒,但会编码 —— 而编码后的目录名不可读。** 实测:

```
"_shared"     → _h_69dddf655795248ef9da26e0e5345de6
"shared"      → shared
"__shared__"  → _h_4342aed7adbf3be5fb9b5c02af2c311b
"SHARED"      → SHARED
```

白名单要求首字符是 `[A-Za-z0-9]`,所以 `_` 开头的一律走 SHA-256。
运维在服务器上 `ls` 看到 `_h_69dddf…` 而不是 `_shared`,排障时这个可读性
是值钱的(见 `encodeSegment` 的说明)。

⇒ **哨兵值应当选 `shared` 这类纯字母形式**,不要 `_shared`。

⚠️ **但这带来一个新的碰撞面**:一个**真实用户**的 `userId` 完全可能就是
`shared`。那时他的工作区与整租户的共享区是同一个目录。
必须在 `tenant-map` / `subject` 层把哨兵值列入保留字并拒绝,
而这是一条**新的、必须被守卫盯住的不变式** —— 否则它就是下一个静默 bug。

### ② `metering` 会不会把整租户算成一个人

**会。** `RawUsage.subjectId` 是归属键,`query({ tenantId, subjectId })` 按它过滤。
一租户一进程下,进程里所有 agent 共用同一个 principal,于是**整租户的用量
全部记在哨兵 subject 名下**。

后果分两面:

- **计费**:按租户计费的产品**不受影响**(反而更简单)
- **计费粒度**:「谁用掉了多少」这个问题**答不出来** ——
  而那是 ToB 客户的第二个问题(第一个是「一共花了多少」)

⇒ 若采纳,必须换一条归属通路:用量事件里带上**真实发起人**,
而不是从执行时的 principal 取。会话簿里存着 `session.subjectId`(真实的),
所以这条路存在 —— 但那意味着**计量与隔离的身份来源正式分家**,
要在文档里写死,否则下一个人会以为它们总是一致的。

### ③ `policy` / `audit` 的语义还成不成立

- **配额**:与 ② 同源。`check(subjectId)` 若拿到哨兵值,配额就是**租户级**的,
  个人配额消失。租户级配额本身是合理产品形态,但它是**另一个产品决策**,
  不能靠隔离档的选择顺带定下来。
- **审计**:`actor` 目前取自 Admin Key 的 label 或会话的 subjectId,
  **不读执行时的 principal** —— 所以审计不受影响。这一条是好消息。

### ④ 产品层代价:同公司用户看得见彼此的文件

这是**决定性的一条,而且它不是技术问题**:

- 对**协作**场景可能正是特性 —— 一个团队共用一个工作区,互相看得见对方的产出
- 对「每人一个私密工作区」的诉求则**根本不行**

而 DSHWAR 的工作区模型(V0.4.1 的四段路径)恰恰是按后者设计的:
`{root}/{tenantId}/{userId}/{workspaceId}`,**userId 是路径的一段**。
一租户一进程把那一段变成常量,等于把工作区模型从「每人一个」降级成「每租户一个」。

## 结论

**技术上可行,但它不是「团队档」的复活。**

「团队档」原来的承诺是「团队内多用户,每人有自己的工作区,便宜」。
一租户一进程给的是「团队共用一个工作区,便宜」—— **少了中间那一条**,
而那一条恰恰是 V0.4.1 花了一整版做的东西。

所以这是**一个不同的产品形态**,该不该有取决于:

> **目标客户要的是「团队共享工作区」,还是「每人私密工作区」?**

若两者都要,那就是两个档,而不是一个档的两种配置 —— 因为它们的
计量粒度、配额粒度、工作区模型全都不同。

**建议**:等 V0.5.5 工作台后端把「工作区」的产品语义定清楚之后再回来看这个。
在那之前不排期 —— 现在做等于用一个技术方案去猜一个还没定的产品问题。

## 已经做了的一件:`shared` 成为身份层保留字(V0.4.7)

**这个形态尚未采纳,但保留字现在就定。**

理由是时机不可逆:保留字必须**在有存量数据之前**定下来。等到将来真走这条路
时再处理碰撞,手里已经有一批 id 是 `shared` 的真实用户,那时只剩迁移一条路。
**现在保留的成本是零**(拒绝一个几乎不会有人用的 id),将来的代价是一次迁移。

实现在 `packages/principal/src/principal.ts` 的 `RESERVED_IDS`,
与 `fs-tenant` 的 `DEFAULT_WORKSPACE_ID`(`default`)同款处理。
⚠️ 保留的是 **id**,不是 tenantId —— 一家公司真的可能叫 `shared`。
