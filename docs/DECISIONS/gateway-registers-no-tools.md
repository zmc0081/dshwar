# 决策待定:网关一个工具都没注册

> **状态**:✅ **已裁决并落地**(2026-08-25)。出厂带 `dsh-tool-fs`,其余 opt-in。
> harness:`docs/UPSTREAM-ISSUE-retest/no-tools.mjs` 与 `real-tools.mjs`

## 事实

`gateway/src/runtime.ts` 的 `GATEWAY_PLUGINS` 装了 `@deepseek-ai/dsh-tools`
(工具**运行时**),但**没有装任何工具包** —— 上游的 `dsh-tool-fs` /
`dsh-tool-bash` / `dsh-tool-fs-search` 等一个都不在。
`profiles/gateway.yml` 同样没有。`DELIBERATELY_OMITTED` 里也没有它们。

⇒ **今天的 agent 做不了任何文件操作。**

## 是刻意的吗 —— 不是,是一条掉在「未验证项」里的缺口

全仓唯一提到这件事的地方是 `docs/FEASIBILITY-REPORT-V2.md` §六「遗留未验证项」:

> **工具调用链路** —— 本次没有注册任何工具,`tool/call` / `tool/result`
> 未实测。网关要暴露工具执行状态时需要补

这句话写于 V0.2.0,之后**七个版本没有再出现过**。它:

- **不是**一条决策(没有 `docs/DECISIONS/` 条目)
- **不是**「自建者自己注册」的声明(README / DEPLOYMENT 都没这么说)
- **不是** `DELIBERATELY_OMITTED` 的一员(那三条各自写了理由)

而且它当时的措辞把问题框成了**展示问题**(「网关要暴露工具执行状态时需要补」),
不是能力问题。⇒ 一条被记成「以后要补的显示功能」的事,实际是「agent 什么都做不了」。

🚨 **与本仓反复记的那一族同形**:一个前提被写进「未验证」清单,
然后下游所有东西开始依赖它 —— 而清单本身没有人再读。

## ⚠️ 关键:它是 fail-closed 还是静默无能力?**两者都有,而危险的那一半是默认路径**

实测(`no-tools.mjs`,零工具,真实驱动一轮):

| 情形                             | 发生了什么                                       | 用户看到                                  |
| -------------------------------- | ------------------------------------------------ | ----------------------------------------- |
| **B · 模型仍然发出 `read` 调用** | `tool/result isError=true`:`unknown tool "read"` | ✅ 拒绝,可核对                            |
| **A · 模型不调工具,直接作答**    | **零 `tool/call`、零错误、零信号**               | 🚨 一句「我已经读完了 note.txt,内容是……」 |

而且实测到一条更要紧的:

> **模型根本不被告知「这里没有工具」** —— 请求里**没有 `tools` 字段**,
> 系统提示里也不提工具(`systemMentionsTools: false`)。

⇒ 一个被训练成「我有文件工具」的模型,在这里得不到任何相反的信号。
**A 才是实际会走的那条路**,而 A 上没有任何东西挡在中间。

这正是 CLAUDE.md 一路在追的**假成功回执**:
一个说自己读完了文件的 agent,与一个真读了的 agent,在界面上完全一样,
而系统里没有任何东西能反驳它。

⚠️ 与 billing 那条「落到 401」**不同族**:401 是**有东西表了态**。
这里是**没有任何东西表态**。

## 它影响什么

下面每一条都建立在「agent 会执行工具」之上,而那件事今天不发生:

| 依赖它的东西                          | 今天的实际状态           |
| ------------------------------------- | ------------------------ |
| `fs-tenant` 的路径钉死                | 守着一条没有人走的路     |
| 策略预授权(允许的工具 / 路径)         | 没有工具可授权           |
| 工作台的工具调用折叠(约束 1)          | 没有工具调用可折叠       |
| V0.4.7「principal 抵达 agent 执行层」 | 执行层今天不执行任何东西 |
| 隔离模型的整套论证                    | 守的是一件还没发生的事   |

## 顺带:怎么接才对,已经实测出来了

见 `docs/DECISIONS/principal-scope-binding.md` 的 2026-08-25 实测:
装上 `dsh-tool-fs` 之后,**每个会话的工作区靠 `meta.cwd` 传递**,
上游工具把它作为 `opts.cwd` 送进 `ctx.fs.resolve()` —— 两个 principal
并发读同名文件,各自拿到自己那份,无串号。

⇒ **接工具与解决逻辑档隔离是同一件事**,不是两件。
而 `gateway/src/runtime.ts` 的 `createAgent` 今天**不传 `meta.cwd`**。

## ✅ 裁决(2026-08-25)与落地

### ① 出厂带 `dsh-tool-fs`,由 `fs-tenant` 治理;其余工具 opt-in

**不是**「自建者自行注册」。理由:**`fs-tenant` 存在的全部意义就是隔离文件操作,
出厂不带任何文件工具,等于发一把锁没有门。**

bash / 网络 / 其余一律 opt-in —— 那是部署方的安全决定,不是基座替他做。
与「不做场景 Skills、不做生态连接器」不冲突:那两条说的是**应用层能力**,
而文件读写是**基座自己的隔离对象**。

连带接线:`createAgent` 传 `meta.cwd = tenantWorkspaceRoot(root, principal)`。

### ② 模型必须被告知这个部署有哪些工具

`renderToolInventory()` 进系统提示(order 100)。零工具时明说
「本部署未注册任何工具……**不要声称你做过这些操作**」。

零工具是合法配置(纯对话部署),所以**不 fail closed** ——
但「没有工具」与「模型不知道有没有工具」是两回事,后者是缺陷。

### ③ 这件事排在逻辑档之前

逻辑档那件事至少是**沉默**的;这件事会**主动产生一个看起来成功的回答**。

## 🚨 接线第一次真跑,抓到两个从未被触发过的缺陷

**两个都在 `fs-tenant` 里,都在安全相关的路径上,而且都是「出厂不带工具」直接掩盖的** ——
本类的隔离逻辑**从来没有走过真实的工具路径**。

### 缺陷一:`TenantFileSystem` 没声明 `inject`

cordis 把 `this.ctx` 重绑到**访问方**的上下文。从根上直接调 `ctx.fs` 没问题;
而经 agent 的工具层调进来时,访问方的 ctx 带着 inject 保护,于是:

```
Error: cannot get property "principal" without inject
```

**每一次文件操作都失败**,而失败信息是一句 cordis 的内部错误,
与租户隔离毫无字面关系 —— 排查时最容易被当成装配问题。

### 缺陷二:`cwd` 与请求路径用了同一个判据

| 输入             | 来自谁                   | 绝对路径意味着               |
| ---------------- | ------------------------ | ---------------------------- |
| `path`(请求路径) | **模型**                 | 逃逸企图 —— 拒绝是对的       |
| `cwd`(工作目录)  | **会话头**(我们自己写的) | 正常 —— 上游要求它是绝对路径 |

当时两者都走 `pinPath`,而它「绝对路径一律拒绝」。于是上游把会话头里的
绝对 cwd 传进来,每次操作都报「不接受绝对路径」。

⇒ 新增 `pinCwd()`:相对路径照旧钉进根;绝对路径做**包含性检查** ——
根内接受,根外拒绝。⚠️ 请求路径的判据**没有跟着放松**,
两者混为一谈的话 `read("/etc/passwd")` 会变成合法调用(反向对照钉住了这一条)。

## ⚠️ 一处与直觉相反的实测:`meta.cwd` 不是防线,是默认值

裁决里预期的负向验证是「不传 `meta.cwd`,确认落回 anonymous」。**那个失效形态不存在**:
`fs-tenant.resolve()` 在 `opts.cwd === undefined` 时**默认用当前主体的工作区根**,
所以不传它,文件照样落在正确的租户目录。

⇒ 它的价值在别处,而那两处是真的:

1. **不用 `fs-tenant` 的部署**(直接 fs-local)靠它把会话分开;
2. 将来 opt-in 的 `dsh-tool-bash` 用同一个 session cwd 定 workdir,
   **而那条路上没有 fs-tenant 兜底**。

所以负向验证改打在它**可观察**的那一面:会话头里的 cwd 等于该主体的工作区根
(`gateway/test/factory-tools.test.ts` ③)。删掉 `createAgent` 里的 `meta` 之后,
红的是这一条。

## 🚨 记法比结论重要:**一件事被归错类,比被漏记更难发现**

这个缺口不是没被记过。它在 `docs/FEASIBILITY-REPORT-V2.md` §六「遗留未验证项」里
躺了**七个版本**,原话是:

> **工具调用链路** —— 本次没有注册任何工具,`tool/call` / `tool/result` 未实测。
> **网关要暴露工具执行状态时需要补**

问题出在最后那半句:它把这件事归成了**展示问题**(「要暴露执行状态时」),
而实际是**能力问题**(「agent 什么都做不了」)。

| 如果归类为   | 读清单的人会想                   | 什么时候会被拿出来做 |
| ------------ | -------------------------------- | -------------------- |
| 展示问题     | 「等要做工具调用 UI 的时候再说」 | 前端排期时           |
| **能力问题** | 「出厂的 agent 什么都做不了」    | **立刻**             |

⇒ **它在清单上是存在的**,所以每次扫清单的人都会看到它、并且判断「不急」——
判断本身没错,错的是那个判断所依据的分类。

> **漏记的东西会在需要它的时候被发现;归错类的东西不会 ——
> 因为它已经在清单上了,而清单上的东西被认为是"记过了"。**

这一条与本仓「守卫不能惩罚记录」「负向验证不得依赖当前状态」同族:
都不是「有没有做」的问题,是**「做了,但做的那个东西答的是另一个问题」**。

⇒ 落到操作上:往「遗留未验证项」里写一条时,**先问它坏掉的后果是什么**,
按后果归类,不按「将来谁会碰它」归类。
